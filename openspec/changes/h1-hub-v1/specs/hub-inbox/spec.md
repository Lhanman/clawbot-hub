# Spec Delta

## Purpose

规定使用者在微信里发给 ClawBot 的话怎么被收进来、交给哪个项目、项目怎么取、怎么回复。使用者只有一个聊天窗口，所以要有一套规矩决定一句话归谁；这套规矩不能改变 ashare-quant 现在的用法（不带前缀的话一个字不用改）。

服务不理解这些话的意思——"持仓""状态""买 600519 100 1500"怎么认、怎么答，都在各项目里。服务只做：收进来、认人、分发、保证至少送到一次、记下对话凭证好让项目回复。

## ADDED Requirements

### Requirement: 收消息

登录正常时，服务 MUST 在一个后台线程里不停地向腾讯长轮询 `getupdates`（带上次的 `get_updates_buf`，每次最多等 `upstream.poll_timeout` 秒，默认 45，腾讯建议了更长的 `longpolling_timeout_ms` 时用建议值加 10 秒）。收到一批消息 MUST 按这个顺序处理，缺一不可：

1. 先按消息自己的时间 `at_ms` 排序（同一批里收到时间都一样，所以按消息自己的时间排，与 ashare-quant 一致；时间相同的保持原来的先后）。`at_ms` 是腾讯给的 `create_time_ms`，没有就用收到的时间。
2. 在一个数据库事务里：按去重键（腾讯给的 `message_id`，没有就用 `seq`，再没有就用"时间、对话凭证、文字"的摘要）排除已经收过的，把使用者的消息存下来，更新窗口（见 `hub-quota`），为每条算好交给谁、建好待取记录；
3. 事务提交以后，才把新的 `get_updates_buf` 写回凭证文件（写回的规矩见 `hub-login`）。

这样服务在两步之间被杀，重启后腾讯会再给一遍，去重键保证不会收两次（待确认：腾讯在客户端带着旧的 `get_updates_buf` 再请求时会重发同一批消息，ashare-quant 现在就依赖这一点，列入真机验证清单）。错误处理沿用 ashare-quant 现在的做法：长轮询没等到消息（读超时）算没有新消息；连不上、HTTP 5xx、`ret` / `errcode` 非 0 都不能当成"没有新消息"，等一等再收，等待时间从 `upstream.backoff_start`（5 秒）起每次翻倍、最多 `upstream.backoff_max`（60 秒），收到一批正常的消息后重新计；-14 的判断顺序和处理见 `hub-send`、`hub-login`。

文字取法：这条消息里所有文字项（`type` 为 1）的文字依次拼接；没有文字项（图片、语音、文件……）时 `has_text` 为 false、文字为空。没有对话凭证的消息不能回复，也就不收（不建待取记录、不开窗口，日志里记数量）。

去重用的"已收过"记录（`inbound_seen`）保留 7 天。

#### Scenario: 收到一句话

- **WHEN** 假上游返回使用者的一条消息 `持仓`，对话凭证 `ctx-1`
- **THEN** 数据库里多一条待取记录，开了新窗口、对话凭证是 `ctx-1`，凭证文件里的 `updates_buf` 更新成上游给的新值

#### Scenario: 重复的消息只收一次

- **WHEN** 假上游把同一条消息（同一个 `message_id`）连续返回两次
- **THEN** 只有一条待取记录，窗口只开一次

#### Scenario: 两步之间被杀

- **WHEN** 事务已提交、`updates_buf` 还没写回时服务被杀，重启后假上游又返回同一批消息
- **THEN** 不产生重复的待取记录

#### Scenario: 一批消息按消息自己的时间排

- **WHEN** 假上游一次返回三条消息，在批里的先后是 C、A、B，它们自己的时间是 10:03、10:01、10:02
- **THEN** 待取记录的先后是 A、B、C；项目取话时也是这个先后

#### Scenario: 多个文字项依次拼接

- **WHEN** 一条消息有两个文字项 `持仓` 和 `详情`，另一条只有一张图片
- **THEN** 前者的文字是 `持仓详情`，`has_text` 为 true；后者文字为空，`has_text` 为 false

#### Scenario: 没有对话凭证的消息不收

- **WHEN** 假上游返回一条使用者的消息，没有 `context_token`
- **THEN** 没有待取记录，窗口不变，不回复

#### Scenario: 腾讯报错不是"没有新消息"

- **WHEN** 假上游对 `getupdates` 回 `ret: 500`，再回 HTTP 502，再恢复正常
- **THEN** 等待时间依次是 5 秒、10 秒，恢复后重新计；期间没有项目收到任何东西，`hubctl status` 里最近一次收消息的错误可见

#### Scenario: 腾讯建议了更长的等待

- **WHEN** 假上游在返回里给 `longpolling_timeout_ms: 60000`
- **THEN** 之后的长轮询读超时是 70 秒

### Requirement: 只认使用者本人

只有 `from_user_id` 等于凭证里的 `user_id` 的消息才会进入后面的流程。其他人发给 ClawBot 的消息 MUST 被丢弃：不看内容、不转给任何项目、不回复、不开窗口、不记正文；只给"忽略了几条"计数，日志里写数量。腾讯标明是机器人自己发的消息（`message_type` 为 2）同样丢弃。

#### Scenario: 陌生人发来的消息

- **WHEN** 假上游返回一条 `from_user_id` 不是使用者的消息
- **THEN** 没有待取记录，没有回复，窗口不变，`hubctl status` 里"忽略的消息"加 1

#### Scenario: 机器人自己发的消息

- **WHEN** 假上游返回一条 `from_user_id` 是使用者、但 `message_type` 为 2（机器人）的消息
- **THEN** 同样丢弃：没有待取记录，窗口不变，不回复，"忽略的消息"加 1

### Requirement: 一句话交给谁

服务 MUST 按下面的顺序决定每一句话的去向，第一个命中的生效。匹配时去掉首尾空白，全角空格当空格，英文不分大小写、全角半角视为相同（按 Unicode NFKC 比较）。**分隔符**指空白和 `:` `：` `,` `，` `、`。交给项目的文字是去掉前缀和紧跟着的**全部**分隔符以后、从原始字符串里按位置切出来的内容（NFKC 不改变交给项目的文字），再去掉首尾空白；没有前缀的话也去掉首尾空白（ashare-quant 的指令解析本来就先去空白）。

1. **没有文字**（图片、语音等）：交给默认项目（文字为空、`has_text` 为 false）；默认项目的情形见第 5 步。
2. **服务自己的指令**：话是 `hub.label`（默认"服务"），或者它后面跟着分隔符：由服务回复，不交给任何项目（见下一条）。"服务器状态"这样词后直接连着字的不算。
3. **带前缀**：话以某个项目的前缀开头，后面紧跟分隔符或者就此结束：交给那个项目，去掉前缀和分隔符。前缀后面直接连着字（"量化因子"）**不算**带前缀，这样默认项目自己的指令里碰巧以前缀开头的字不会被误拦。项目已停用时由服务回"项目「x」已停用，这句话没处理"，不入队。
4. **确认话**：整句话（去掉首尾空白以后）正好是一个确认词（`routing.confirm_words`，默认对、是、确认），并且有项目在等确认（见"等确认"）：恰有一个就交给它；有几个就由服务回"有几个项目在等你确认（量化、x），请加前缀，例如“量化 对”"（括号里是各项目的称呼，例子里用第一个项目和使用者发的那个词）；一个都没有就往下走。
5. **其余的话**：交给默认项目；默认项目已停用时由服务回"项目「量化」已停用，这句话没处理"，不入队；没有默认项目由服务回"没有设默认项目，这句话没处理：请加项目前缀（发“服务 项目”看有哪些）"。

交给项目的每一条待取记录带着它是怎么路由来的（`via`：`prefix`、`confirm`、`default`）。`via` 是 `confirm` 时，由项目自己判断这句话是不是它要的确认，不是就当普通话处理。

上面方括号里写的"称呼"是服务对使用者提到一个项目的统一叫法：有前缀用前缀，没有前缀用项目名（见 `hub-projects`）。

#### Scenario: 不带前缀归默认项目

- **WHEN** 默认项目是 ashare-quant（前缀"量化"），使用者发"持仓"
- **THEN** ashare-quant 的待取记录里文字是"持仓"、`via` 是 `default`

#### Scenario: 带前缀归对应项目

- **WHEN** 项目 x 的前缀是 `x`，使用者发"x 状态"、"X：状态"、"x，状态"
- **THEN** 三句都交给项目 x，文字都是"状态"

#### Scenario: 连着好几个分隔符

- **WHEN** 使用者发"x，，  状态"和"x：  "
- **THEN** 前一句交给 x，文字是"状态"；后一句交给 x，文字为空，`has_text` 为 true

#### Scenario: 默认项目也能带前缀

- **WHEN** 使用者发"量化 状态"
- **THEN** 交给 ashare-quant，文字是"状态"，`via` 是 `prefix`

#### Scenario: 前缀后面直接连着字

- **WHEN** 使用者发"量化因子"（前缀"量化"后面没有分隔符）
- **THEN** 当作没有前缀，原样交给默认项目

#### Scenario: 不认识的前缀

- **WHEN** 使用者发"foo 状态"，没有叫 foo 的前缀
- **THEN** 原样（含"foo"）交给默认项目

#### Scenario: 只发了一个前缀

- **WHEN** 使用者发"x"
- **THEN** 交给项目 x，文字为空，`has_text` 为 true

#### Scenario: 没有前缀的话也去首尾空白

- **WHEN** 使用者发"  持仓  "（前后有空格，含全角空格）
- **THEN** 交给默认项目的文字是"持仓"

#### Scenario: 图片

- **WHEN** 使用者发了一张图片（没有文字项）
- **THEN** 交给默认项目，文字为空、`has_text` 为 false；没有默认项目时服务回第 5 步那句"没有设默认项目……"

#### Scenario: 没有默认项目

- **WHEN** 没有默认项目，使用者发"持仓"
- **THEN** 没有项目收到；服务回"没有设默认项目，这句话没处理：请加项目前缀（发“服务 项目”看有哪些）"

#### Scenario: 默认项目已停用

- **WHEN** 默认项目 ashare-quant 已停用，使用者发"持仓"，1 分钟后又发"量化 状态"
- **THEN** 两句话都没有入队；只有第一句得到回复"项目「量化」已停用，这句话没处理"，第二句落在同一个目标的限频里（5 分钟内只回一次），什么也不回

#### Scenario: 限频过了以后再提醒

- **WHEN** 同上，使用者隔了 6 分钟又发一句"持仓"
- **THEN** 这句话同样没有入队，服务再回一次"项目「量化」已停用，这句话没处理"

### Requirement: 服务自己的指令和提示

服务自己说的话只有两类：两个指令的回答，和路由时的提示。它们的第一行都以 `【服务】` 开头（标签 `hub.label`，默认"服务"，指令词也是它），算"回复"一类的条数，记在内部名字 `_hub` 名下（见 `hub-projects`）。

- `服务 项目`：列出每个启用的、能收话的项目的称呼、是不是默认、在不在线，例如 `量化（默认，在线）：不加前缀的话都给它，也可以写“量化 …”`、`x（离线）：写“x …”交给它`。只推送的、已停用的项目不列。
- `服务 状态`：登录状态、对话窗口还剩多久、已用 / 总条数、各项目在不在线，不含任何凭证和密钥。
- "服务"后面是别的字（或没有字）时回一句"我只认两个指令：服务 项目、服务 状态"（词取 `hub.label`）。

路由时的提示：没有默认项目、项目已停用、项目没在线、项目积压（后两种见下）这四种，同一种对同一个目标在 `inbox.offline_notice_seconds`（默认 300）秒内最多回一次，免得使用者连发几句就收到一串一样的话；被限频的那一次什么也不回（话本身照常处理：入队，或没处理）。上次提醒的时间记在数据库里，重启不清零。"有几个项目在等你确认"和两个指令的回答不限频。

服务自己的回复 MUST 尽力而为、至多一次：由单独的发送线程按顺序发，收消息的线程把它放进队列就继续收，不等它发完；服务在放进队列之后、发出之前被杀，这条回复丢了不补（话本身已经按规则入队或处理，没有丢）。补收到的旧消息触发的服务回复，如果对话凭证已经过了窗口，发不出去就算了，不重试、不告警。指令本身和"没地方可去的话"不存正文。

#### Scenario: 服务 项目

- **WHEN** 使用者发"服务 项目"，启用着 ashare-quant（前缀量化、默认、在线）、x（前缀 x、离线）和一个只推送的项目
- **THEN** 收到的回复第一行以 `【服务】` 开头，里面有"量化（默认，在线）"和"x（离线）"，没有只推送的项目；没有交给任何项目

#### Scenario: 服务 状态不带凭证

- **WHEN** 使用者发"服务 状态"
- **THEN** 回复里有登录状态、窗口剩余、已用条数；找不到 `bot_token`、`context_token`、项目密钥

#### Scenario: 服务的回复算回复

- **WHEN** 使用者发"服务 状态"，服务回复一条
- **THEN** 新窗口里"回复"一类的已用条数是 1（记在 `_hub` 名下），不占任何项目的保底和上限；这句话本身开了新窗口，所以一定有额度可回

#### Scenario: 服务也不理解别的话

- **WHEN** 使用者发"服务 重启"，另一次发"服务器状态"
- **THEN** 前者服务回"我只认两个指令：服务 项目、服务 状态"，什么也没改；后者不是指令，原样交给默认项目

#### Scenario: 改了标签指令词跟着变

- **WHEN** 配置 `hub.label: 助手`，使用者发"助手 状态"，另一次发"服务 状态"
- **THEN** 前者得到状态回答，回复第一行以 `【助手】` 开头；后者原样交给默认项目

#### Scenario: 同类提示限频

- **WHEN** 项目 x 没在线，使用者 1 分钟内给它发 3 句话；又在没有默认项目时连发 2 句无前缀的话
- **THEN** 使用者收到一条"x 没在线"和一条"没有设默认项目"，共两条；3 句发给 x 的话都在它的队列里

#### Scenario: 发送被占着时继续收消息

- **WHEN** 全局发送锁被别的项目的发送占着 30 秒，这时来了一批消息，其中一句需要服务回复
- **THEN** 这批消息马上入库、`updates_buf` 写回、下一次长轮询照常开始；回复等发送锁空了再发

#### Scenario: 回复丢了不补

- **WHEN** 服务把一条回复放进队列后、发出之前被 `kill -9`，重启后假上游不再返回那句话
- **THEN** 那句话已经按规则入队（若该入队），使用者没收到那条回复，重启后也不补发

### Requirement: 等确认

项目在回复里带 `awaiting_confirmation: true`（见 `hub-send`），就是在告诉服务"我在等使用者回确认话"。服务 MUST 为每个项目记一个等确认标记（最多一个，记到什么时候）：

- **写入**：回复结果的 `parts_sent` 至少为 1（`sent`、`unconfirmed`、`partial`）时，写入 `发送完成的时刻 + confirm_seconds`（回复里没给就取 `routing.confirm_seconds`，默认 600 秒）。`rejected`、`failed`、`skipped` 不写。被回复的那句话之后，这个项目又收到过新的话也不写；"之后"按 `(at_ms, 入库先后)` 比较，与取话的排序一致（同一批里时间相同的话按入库先后）。
- **清除**，只在这几个时刻：到期；这个项目收到任何话（包括被确认话消耗的）；这个项目被停用；收到确认话的那一刻这个项目不在线（见 `hub-projects`，当场判断，不需要后台任务）。交给服务自己的指令、交给别的项目的话，不动任何项目的标记。服务重启不清（项目自己等确认的状态在内存里，重启就丢了；此时使用者回"对"会交给项目，项目回"没有等你确认的记录"，这是预期的）。

标记只影响第 4 步的确认话，不影响带前缀的话。

#### Scenario: 对不串线

- **WHEN** 项目 A 的回复带 `awaiting_confirmation: true`（等确认），项目 B 没有，使用者发"对"
- **THEN** "对"交给 A，`via` 是 `confirm`

#### Scenario: 几个项目同时在等

- **WHEN** A、B 的回复都带 `awaiting_confirmation: true`，使用者发"对"
- **THEN** 没有项目收到；服务回"有几个项目在等你确认（量化、x），请加前缀，例如“量化 对”"；使用者再发"量化 对"，交给 A

#### Scenario: 超过 10 分钟

- **WHEN** A 等确认，11 分钟后使用者发"对"
- **THEN** 当作没有项目在等，原样交给默认项目

#### Scenario: 中间说了别的

- **WHEN** A 等确认，使用者先发"持仓"（交给默认项目 A），再发"对"
- **THEN** "持仓"交给 A 的同时清掉了等确认的标记；"对"当作没有项目在等，交给默认项目（A 回"没有等你确认的记录"，和现在一致）

#### Scenario: 问服务和别的项目不影响

- **WHEN** x 等确认，使用者先发"服务 状态"，再发"y 状态"（交给另一个项目 y），最后发"对"
- **THEN** "对"仍交给 x

#### Scenario: 没有人在等

- **WHEN** 没有项目在等确认，使用者发"对"
- **THEN** 原样交给默认项目

#### Scenario: 等确认的项目停用或不在线

- **WHEN** 默认项目 A 在线；x 等确认，x 被停用，使用者发"对"；另一次是 x 等确认，x 的取话停了 2 分钟（不在线），使用者发"对"
- **THEN** 两次都当作没有项目在等，原样交给默认项目 A；x 的标记已清掉

#### Scenario: 服务重启不清标记

- **WHEN** x 等确认，服务重启（x 重新取话），使用者发"对"
- **THEN** "对"交给 x

#### Scenario: 回复期间使用者抢先回了

- **WHEN** 默认项目 A 的一条带 `awaiting_confirmation` 的回复分三条发送，发出第 1 条后使用者回了"对"，它按"没人等"交给了默认项目 A，回复才发完
- **THEN** 不写标记（被回复的那句话之后 A 又收到过新话）；使用者再发"对"仍按没有人在等处理

### Requirement: 项目没在线

交给一个**不在线**的项目（定义见 `hub-projects`）的话，服务 MUST 仍然把它放进这个项目的待取队列，保留 `inbox.retention_minutes`（默认 10）分钟，并马上回使用者一句：`「<称呼>」现在没在线。这句话我先留着：<N> 分钟内它回来就会处理，超过就作废`（N 是 `inbox.retention_minutes`）。这句提醒受上面的限频约束。保留期从**收到**起算（服务停了很久以后补收到的旧消息也会交出去，项目用消息自带的时间自己判断要不要注明"回复你 HH:MM 发的消息"）。

#### Scenario: 项目没在线

- **WHEN** 项目 x 90 秒内没有取过话，使用者发"x 状态"
- **THEN** 使用者马上收到服务的回复，说明 x 没在线、话留 10 分钟；这句话在 x 的队列里

#### Scenario: 回来以后接着处理

- **WHEN** 上面的 x 在 5 分钟后开始取话
- **THEN** 取到"状态"，`attempt` 为 1

#### Scenario: 超时作废

- **WHEN** x 在 11 分钟后才回来取话
- **THEN** 取到的是空，那条记录标成"过期"，正文已清空

#### Scenario: 处理慢指令时使用者又发话

- **WHEN** 项目取走一句话后处理了 120 秒（期间按 `hub-client` 的做法每 30 秒发一次心跳），使用者在第 60 秒又给它发了一句
- **THEN** 使用者没有收到"没在线"的提醒，新话进了队列，处理完第一句后取到

### Requirement: 取话

`GET /v1/inbox?wait=<秒>&max=<条数>` MUST 返回分给调用方这个项目的话，不含别的项目的：

```json
{
  "items": [
    {"id": "m_9f3a1c20", "text": "持仓", "has_text": true,
     "at": "2026-10-12T08:31:02+08:00", "at_ms": 1791765062000,
     "received_at": "2026-10-12T08:31:03+08:00", "attempt": 1,
     "via": "default", "reply_handle": "rh_Zk3pQ2..."}
  ],
  "lease_seconds": 60
}
```

- `wait`：没有话时最多等几秒再返回空列表，默认 `inbox.wait_seconds`（25），0 表示不等；超过 `inbox.max_wait`（55）的截成 55；负数、不是整数的返回 400 `bad_request`。等的时候一有新话立刻返回。
- `max`：最多返回几条，默认 10，超过 50 的截成 50；负数、不是整数的返回 400 `bad_request`；`max=0` 合法，不租出任何话、立刻返回空列表（`wait` 被忽略），用来当心跳。
- 返回的话按 `at_ms` 先后排，`at_ms` 相同的按入库先后；每一条被**租出去** `inbox.lease_seconds`（默认 60）秒，租期内不会再给；租期过了还没确认，下次取话时再给一次，`attempt` 加 1，`reply_handle` 不变。最多租出 `inbox.max_attempts`（默认 5）次，租出 5 次都没确认的，之后不再给，由定时清理作废并记一条事件（见"清理"）。
- 保留期适用于所有没确认的话：没租出去过的话，或者租期已结束的话，只要收到已经超过 `inbox.retention_minutes`，就不再交出，标成"过期"（取话时现判断，清理任务也会处理）。正在租期内的话不受影响。
- 返回之前（包括被新话唤醒时）MUST 再核对一次这个项目是否仍启用：已停用的以 403 `project_disabled` 结束，不交出任何话。
- 同一个项目同一时间只留一个正在等的取话请求：新的来了，旧的马上返回空列表。
- 每个项目的队列最多 `inbox.max_queued`（默认 50）条，超了丢最旧的没租出去的（标成"作废"，清掉正文和对话凭证），并记一条事件。队列里的话全是租出去的、没有可丢的（项目取走了很多话却一直没确认）时，丢掉新来的这一句（标成"作废"，不建待取记录），记一条事件，并回使用者一句`「<称呼>」积压太多，这句话没收`（"项目积压"这一类提示，限频规则同上）。
- 只推送的项目（`--push-only`）调这个接口：403 `push_only`。

#### Scenario: 有话立刻返回

- **WHEN** 队列里有一条话，项目调 `GET /v1/inbox?wait=30`
- **THEN** 马上返回这一条，不等

#### Scenario: 没话就等

- **WHEN** 队列是空的，项目调 `GET /v1/inbox?wait=2`，1 秒后使用者发来一句话
- **THEN** 大约 1 秒时返回这句话；如果没人发话，大约 2 秒时返回空列表

#### Scenario: wait 和 max 的边界

- **WHEN** 项目依次调 `wait=100`、`wait=-1`、`wait=abc`、`max=100`、`max=0`
- **THEN** 第一次按 55 秒等（测试里用假时钟看到上限是 55）；第二、三次 400 `bad_request`；第四次最多返回 50 条；第五次立刻返回空列表且队列里的话没被租出

#### Scenario: 没确认会再给

- **WHEN** 项目取走一条话但没确认，租期 60 秒过去后再取
- **THEN** 再次拿到同一条（同一个 `id`、同一个 `reply_handle`），`attempt` 是 2；在租期内再取不会拿到

#### Scenario: 超过最多次数

- **WHEN** 同一条话被租出 5 次都没确认，第 5 次租期结束后项目又取话，随后定时清理跑了一轮
- **THEN** 取话拿不到它；清理之后它是"作废"，正文和对话凭证已清空，事件里有一条记录

#### Scenario: 租出去的话也受保留期约束

- **WHEN** 一条话在第 9 分钟被取走、没有确认，租期结束时已是第 10 分钟之后
- **THEN** 不再交出，记录标成"过期"

#### Scenario: 只看得到自己的

- **WHEN** 使用者先后发了给项目 A 和项目 B 的话，两个项目各自取话
- **THEN** 各自只拿到自己的

#### Scenario: 新请求顶掉旧请求

- **WHEN** 项目有一个取话请求正在等，同一项目又发来一个
- **THEN** 旧的马上返回空列表，新的继续等

#### Scenario: 队列满了丢最旧的

- **WHEN** 项目 x 没在线，使用者给它连发 51 句话
- **THEN** 队列里留下后 50 句，最早的一句是"作废"、正文已清空，事件里有一条记录

#### Scenario: 队列里全是租出去的话

- **WHEN** 项目 x 一次 `max=50` 取走了 50 句话、都没有确认，使用者又发来第 51 句
- **THEN** 这 50 句仍在租期里、不受影响；第 51 句是"作废"、没有待取记录，事件里有一条记录，使用者收到「x」积压太多、这句话没收；5 分钟内再发一句，话同样没收，但不再重复提醒

#### Scenario: 只推送的项目取话

- **WHEN** 只推送的项目调 `GET /v1/inbox`
- **THEN** 403 `push_only`

### Requirement: 确认

`POST /v1/inbox/ack`，请求 `{"ids": ["m_…", …]}`（最多 50 个，超过返回 400 `bad_request`，空列表合法），MUST 把这些话标成"已处理"：不再给，并**立即清掉它们的正文**（回复用的对话凭证留到回复句柄失效，见"回复句柄"）。返回 `{"acked": <n>, "unknown": ["m_…", …]}`：租出去的话（包括租期已过但还没被重新租出的）算 `acked`；已经确认过的、已过期、已作废的、不属于调用方的、不存在的都不报错（幂等），算在 `unknown` 里，不透露是哪一种。

项目 SHOULD 在**处理完**以后再确认（先确认后处理会在项目挂掉时丢话；先处理后确认会在挂掉时多处理一次，项目对同一句话处理两次应当无害）。

#### Scenario: 确认以后不再给

- **WHEN** 项目取到一条话，确认，租期过后再取
- **THEN** 取不到它；数据库里这条记录没有正文

#### Scenario: 租期过了才确认

- **WHEN** 项目取到一条话，处理了 70 秒（租期已过但没有再取过话），然后确认
- **THEN** 这条话算 `acked`，不在 `unknown` 里

#### Scenario: 重复确认

- **WHEN** 同一个 `id` 确认两次，或者确认一个别的项目的 `id`、一个不存在的 `id`
- **THEN** 都是 200，第二次 / 别人的 / 不存在的出现在 `unknown` 里，没有任何副作用

#### Scenario: 确认已经作废的话

- **WHEN** 确认一条已经过期的话和一条已经作废的话
- **THEN** 两条都在 `unknown` 里，记录没有变化

#### Scenario: 一次确认太多

- **WHEN** 一次确认 51 个 `id`
- **THEN** 400 `bad_request`，一条也没有确认

### Requirement: 回复句柄

每条取到的话带一个不透明的回复句柄 `reply_handle`（`rh_` 加 `secrets.token_urlsafe(16)`，共 25 个字符），同一条话每次租出给的都一样。项目用它调 `POST /v1/replies`（见 `hub-send`）。句柄 MUST：

- 只对被路由给这个项目的那条话有效；别的项目拿到它、或者根本不存在，都是 404 `unknown_handle`（两种情况返回一样）；
- 有效期是 `min(话被收到之后 reply.handle_minutes（默认 30）分钟, 那句话自己的时间 at_ms 之后 quota.window_hours 小时)`。过了是 410 `handle_expired`，同时清掉那条话的对话凭证。补收到的旧消息（比窗口还旧）照样交给项目，但用句柄回复得 410，原因写"这句话太旧，微信已不能回复"，项目要通知使用者就走 Bark；
- 话已经过期或作废的，以及 `hubctl login` 换了新的登录之后，句柄一律 410 `handle_expired`（换登录时在一个数据库事务里清掉所有待取记录的对话凭证并作废旧窗口，见 `hub-login`；旧凭证不能再拿去发）；话已经确认的，句柄在有效期内仍可用；
- 不含任何对话凭证的信息（句柄和 `context_token` 之间只有数据库里的对应关系，对话凭证从不出现在任何接口里）。

#### Scenario: 句柄用别人的

- **WHEN** 项目 B 用项目 A 的句柄回复
- **THEN** 404 `unknown_handle`，没有发任何东西

#### Scenario: 句柄过期

- **WHEN** 话收到 31 分钟后，项目才回复
- **THEN** 410 `handle_expired`，没有发任何东西

#### Scenario: 确认以后还能回复

- **WHEN** 项目取到一句话、确认，5 分钟后用句柄回复
- **THEN** 回复成功发出；数据库里这条话的正文是空的

#### Scenario: 补收的旧消息

- **WHEN** 服务停了一天半后重启，腾讯补发了一句 30 小时前的话，项目取到它并用句柄回复
- **THEN** 410 `handle_expired`，原因是"这句话太旧，微信已不能回复"，假上游没有收到 `sendmessage`

#### Scenario: 重新登录以后旧句柄作废

- **WHEN** 项目取到一句话，然后 `hubctl login` 绑了新的登录，项目再用句柄回复
- **THEN** 410 `handle_expired`，没有发任何东西

#### Scenario: 句柄里没有凭证

- **WHEN** 检查所有 `reply_handle`
- **THEN** 它们都是随机字符，不是对话凭证的编码或截取

### Requirement: 清理

服务 MUST 每分钟清理一次：

- 租期已过（或根本没租出去）并且收到已超过保留期的话标成"过期"；租期已过并且已租出 `inbox.max_attempts` 次的话标成"作废"并记一条事件；"过期""作废"和"已确认"一样，立即清掉正文，"过期""作废"同时清掉对话凭证；
- 已确认的话，对话凭证在回复句柄失效时清掉；
- 已确认、过期、作废的待取记录保留 7 天（只有编号、项目、时间、路由方式、字数、结果，没有正文和对话凭证），之后删除；
- 收消息的去重记录保留 7 天。

窗口、发送记录和事件的保留期见 `hub-deploy`。

#### Scenario: 过期的话没有正文

- **WHEN** 一条话在队列里放了 11 分钟没人取，清理跑了一轮
- **THEN** 它的状态是"过期"，数据库里正文为空

#### Scenario: 记录保留 7 天后删除

- **WHEN** 一条已确认的记录放了 8 天，清理跑了一轮
- **THEN** 这条记录已不在数据库里；7 天内的仍在，且没有正文
