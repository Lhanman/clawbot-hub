# 迁移手册

把 ashare-quant 现在用着的 ClawBot 凭证迁进共用服务：**不重新扫码，用导入**；**旧的微信问答程序先停、服务再启动，绝不让两个程序同时向腾讯收消息**；每一步都能退回去（见《回退手册》）。

停服务一律用 `launchctl bootout`（说明见《安装说明》）。**导入凭证前必须先停掉服务**，否则两个程序会同时收消息，凭证文件也可能被写乱。

## 谁在场

| 步骤 | 需要使用者本人在场吗 |
|---|---|
| 第 1 步 检查演练遗留 | 不需要，Mac 上的线程可以做 |
| 第 2 步 停旧的微信问答 | **需要**：从这一步到第 8 步一气做完，中间微信问答是断的 |
| 第 3 到 6 步 备份、停服务、导入、启动 | 在场（和第 2 步连着做），其中第 5 步导入失败时才需要重新扫码（手机微信） |
| 第 7 步 ashare-quant 切到 hub 模式 | 在场 |
| 第 8 步 验证 | **需要使用者本人在场**：在手机上给 ClawBot 发一句话，看收到的结果 |
| 第 9 步 观察一个交易日 | 不需要在场，但要看一眼当天的三条消息 |

**挑周末切换**：周末基本没有定时推送，断几分钟没有影响。切换当天先看一眼 ashare-quant 当天有没有要推的东西。

## 开始之前要满足

1. 服务已经按《安装说明》装好，演练做过，演练目录已经移走。
2. ashare-quant 已经有「走服务」的模式（`wechat.mode: direct | hub`，默认 `direct`）。这是 ashare-quant 里另立的变更，**不属于本仓库**；那个变更没做完之前，不要开始切换。
3. 现有的微信问答（`aq wechat serve`）稳定运行，凭证有效。
4. 手边有：ashare-quant 的目录路径（下面写作 `<ashare-quant 目录>`）、服务里登记 ashare-quant 要用的 Bark 设备码（如果还没配）。

## 第 1 步：检查正式数据目录里没有演练遗留

**先看，再动。** 正式数据目录是 `~/.clawbot-hub`。演练用的是 `~/.clawbot-hub-rehearsal`，它们不该有任何交集，但演练时要是忘了设 `CLAWBOT_HUB_HOME`，演练的东西就会落进正式目录。

先跑第一行 `ls`：**目录不存在就已经是干净的，后面的 `hubctl project list`、`hubctl status` 不用跑**——任何 `hubctl` 命令第一次运行都会把数据目录建出来，为了检查反而留下一个空目录没有意义。目录已经有了才接着跑。

```
ls -la ~/.clawbot-hub 2>&1 | head
cd ~/workbench/clawbot-hub
env -u CLAWBOT_HUB_HOME uv run hubctl project list
env -u CLAWBOT_HUB_HOME uv run hubctl status
grep -o '"base_url": *"[^"]*"' ~/.clawbot-hub/account.json 2>/dev/null
```

预期输出（干净）：目录不存在，或者里面没有 `account.json`；`project list` 说没有登记项目（「没有登记项目」之类）；`status` 的「登录」一行是「还没绑定」，「对话窗口」是「还没收到过你的消息」；`grep` 没有输出。

**有遗留就先移走**：`account.json` 里的 `base_url` 是 `127.0.0.1` 开头（指向假腾讯）、或者有演练登记的项目、或者窗口里有演练的用量，都算遗留。

```
launchctl bootout gui/$(id -u)/com.clawbot-hub.serve 2>/dev/null
mv ~/.clawbot-hub ~/.clawbot-hub.rehearsal-leftover-$(date +%Y%m%d)
```

移走以后重新运行上面几条，预期输出是干净的状态。（移走的目录里有演练的日志，留着没坏处，确认没用了再删。）

## 第 2 步：停旧的微信问答　**使用者本人在场**

```
launchctl bootout gui/$(id -u)/com.ashare-quant.wechat
pgrep -fl "aq wechat serve" || echo 没有在运行
```

预期输出：`bootout` 没有输出；`pgrep` 找不到进程，打印「没有在运行」。**确认真的停了再往下**：它要是还在跑，会和服务同时向腾讯收消息。

> 简报、日报、盘中监控这几条发送链路是定时任务，各自读同一个凭证文件、直接连腾讯发消息；切换的这几分钟里它们要是正好触发，会发不出微信（走 Bark），不会出错。所以才挑周末。

## 第 3 步：备份 ashare-quant 的凭证文件

```
cp -p "<ashare-quant 目录>/data/notify/clawbot.json" ~/clawbot-credentials-backup-$(date +%Y%m%d).json
chmod 600 ~/clawbot-credentials-backup-*.json
ls -l ~/clawbot-credentials-backup-*.json
```

预期输出：一行 `-rw-------`、文件大小几百字节。**这份备份里有登录凭证**，不要放进云盘或 git；整个迁移稳定之后再删。它是退回去的唯一凭据（《回退手册》）。

## 第 4 步：确认服务没在运行

```
launchctl bootout gui/$(id -u)/com.clawbot-hub.serve 2>/dev/null
uv run hubctl status | head -1
```

预期输出：第一行是「服务：没有在运行」。（服务还没装过的话，`bootout` 会报找不到，没关系。）

## 第 5 步：导入凭证

```
uv run hubctl import-credentials ~/clawbot-credentials-backup-<日期>.json --probe
```

预期输出：只有摘要，没有任何凭证——`bot_id` 末 4 位、`user_id`（打码）、绑定时间、**窗口还剩多久、已用几条**，最后一句说凭证有效（`--probe` 用导入的凭证向腾讯收一次，只看是不是 -14 和 HTTP 是否 200；**它不处理返回的消息，也不保存新的收消息进度**，所以不会吃掉一条消息）。

和切换前对一下：窗口剩余时间和已用条数应该和 ashare-quant 里最后一次记录的差不多（比如 3 小时前使用者发的话，已用 4 条，导入后显示窗口还剩约 21 小时、推送已用 4 条）。

三种常见的拒绝：

- 「服务在运行」：回第 4 步；
- 「已经有 account.json」：说明第 1 步没清干净，回去看；确实要覆盖才加 `--replace`（旧文件会先备份成 `account.json.bak-<时间>`）；
- 提示凭证已失效（-14）：旧凭证已经过期了。这时才需要**使用者本人**用手机微信重新扫码（`uv run hubctl login`）。注意：重新扫码会让旧凭证作废，之后就不能再退回 `direct` 用备份的凭证了，要退只能把新凭证同样给 ashare-quant 用。遇到这种情况先停下来，告诉使用者。

## 第 6 步：登记项目、启动服务

如果服务里还没登记 ashare-quant：

```
uv run hubctl project add ashare-quant --prefix 量化 --guaranteed 6 --cap 8 --default
```

密钥只显示这一次，马上存好（这就是第 7 步 ashare-quant 要用的密钥）。然后启动服务：

```
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.clawbot-hub.serve.plist
sleep 5
uv run hubctl status
```

预期输出：「服务：在运行」；「登录」一行是已绑定；「对话窗口」的起点、剩余时间、已用条数和第 5 步导入时看到的一致（窗口**没有**被作废）；项目 ashare-quant 一行，离线（它还没来取过话）。

## 第 7 步：把 ashare-quant 切到 hub 模式　**使用者本人在场**

在 ashare-quant 的配置里把微信的模式改成 `hub`，填上服务地址（`http://127.0.0.1:8790`）和第 6 步的密钥（密钥放 `.env`，**不进 git**；具体的配置项名字以 ashare-quant 那个变更为准），然后重启微信问答：

```
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.ashare-quant.wechat.plist
```

预期输出：没有输出；`uv run hubctl status` 里 ashare-quant 变成「在线」（微信问答现在是服务的客户端，一直在取话）。

## 第 8 步：验证　**使用者本人在场**

1. 手动推一条简报：在 ashare-quant 目录运行 `uv run aq brief --push`。预期：**微信和 Bark 都收到**简报（微信走服务，Bark 是 ashare-quant 自己发的）。
2. **在手机微信里给 ClawBot 发一句「状态」**。预期：几秒内收到 ashare-quant 的回复。这一句同时也续了窗口。
3. `uv run hubctl status`：对话窗口刚刚重新开始，ashare-quant 的「本窗口已推送」比之前多了简报那一条，回复数 1。

**两边都收到才算通。** 有一边没收到：先别往下，按《回退手册》退回去，再查。

## 第 9 步：观察一个交易日

下一个交易日，看这三条消息是不是都经服务到了微信，并且和 Bark 那份内容一致：08:30 简报、14:30 盘中小结、18:00 日报。当天晚上运行：

```
uv run hubctl status
uv run hubctl events --limit 30
uv run hubctl doctor
```

预期输出：`events` 里没有「上一次运行没有正常退出」，没有「登录失效」，也没有「告警已送出：服务重启」「告警已送出：微信消息没发出去」这类记录（只看告警：`hubctl events --kind alert`）；`doctor` 没有 ✗。

## 第 10 步：稳定以后

稳定一段时间之后，另立变更：在 ashare-quant 里删掉直连腾讯的代码；其他项目各自接入（看 `docs/clients/接入指南.md`）。到这时才可以删第 3 步的凭证备份。

## 出问题就退

任何一步出问题，停下来，看《回退手册》。**只要中间没有重新扫过码**，备份的凭证就还有效，退回去之后 ashare-quant 照旧工作。
