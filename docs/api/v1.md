# 项目接口 v1

这份文档给不用 Python 的项目看：怎样用 `curl`（或任何 HTTP 客户端）向 clawbot-hub 发消息、取话、回复、确认。用 Python 的项目直接用 `client/clawbot_hub_client.py`，接入的步骤和惯例见 [接入指南](../clients/接入指南.md)。机器可读的描述是同目录的 `openapi.json`（从服务导出，服务本身不开 `/docs` 之类的页面）。

## 约定

| 项 | 说明 |
|---|---|
| 地址 | `http://127.0.0.1:8790`（配置 `server.host`、`server.port`；局域网监听默认关着） |
| 认证 | 请求头 `Authorization: Bearer <项目密钥>`。密钥以 `chub_` 开头，运维用 `hubctl project add` 登记时给出，只显示一次；放在环境变量或不进 git 的 `.env` 里。只有 `GET /v1/health` 不要密钥 |
| 内容 | 请求体和响应体都是 UTF-8 的 JSON；请求体最多 64 KiB，超过返回 413 |
| 时间 | `at`、`received_at` 这类是带时区的 ISO-8601（默认北京时间）；`at_ms` 是和 `at` 同一时刻的毫秒时间戳 |
| 错误 | 非 200 的响应，正文一律是 `{"error": {"code": "…", "message": "…"}}`，`message` 是中文，不含请求的内容；429 另带 `Retry-After` 响应头（整数秒） |
| 限速 | 发消息和回复合计，每个项目每分钟 30 次，不管结果是发出去还是被拒绝；取话和确认不限速 |
| 同步 | 发消息和回复都是**同步**的：服务发完（或确定发不出去）才返回，拿到的就是最终结果，可以据此决定走不走自己的兜底 |
| 不偷偷重发 | 拿不准有没有送到的（读超时、连接被重置、500），服务和客户端都不会重发，由项目自己决定。要重跑也不发两份，请给 `dedupe_key` |

下面的 `curl` 示例假定已经设了两个环境变量：

```bash
export HUB=http://127.0.0.1:8790
export KEY=chub_...   # 你项目的密钥
```

代码块标题是 `bash exec` 的示例是**可执行**的：测试会对着测试服务按顺序真的运行它们，返回要和紧跟着的响应块一致（只比字段和固定的值，不比 `id`、时间、句柄这类每次不同的值）。响应块标题里的数字是 HTTP 状态码。示例之间有先后：取话的示例用到前面造出来的那句话。

## 接口一览

| 接口 | 做什么 |
|---|---|
| `POST /v1/messages` | 发一条消息 |
| `POST /v1/replies` | 回复使用者的一句话 |
| `GET /v1/inbox` | 取使用者发给你项目的话 |
| `POST /v1/inbox/ack` | 确认话处理完了 |
| `GET /v1/status` | 你项目的额度，加上登录和对话窗口的状态 |
| `GET /v1/health` | 探活 |

## GET /v1/health

探活。不要密钥，只说服务活着和版本，不含登录、窗口、项目的任何信息。服务正在关闭时返回 503 `shutting_down`。

```bash exec
curl -s "$HUB/v1/health"
```

```json 200
{"ok": true, "version": "0.1.0", "api": "1"}
```

`api` 是接口版本（字符串）。

## GET /v1/status

你项目自己的额度，加上全局的登录和对话窗口状态；没有别的项目的任何信息。

```bash exec
curl -s "$HUB/v1/status" -H "Authorization: Bearer $KEY"
```

```json 200
{
  "service": {
    "version": "0.1.0",
    "api": "1",
    "send_timeout_seconds": 30,
    "inbox_online_seconds": 90
  },
  "login": {"state": "ok"},
  "window": {
    "open": true,
    "started_at": "2026-10-12T10:00:00+08:00",
    "ends_at": "2026-10-13T10:00:00+08:00",
    "seconds_left": 86400
  },
  "quota": {
    "limit": 10,
    "used": 2,
    "free": 8,
    "project": {"guaranteed": 6, "cap": 8, "used": 2, "left": 4, "replies_used": 0}
  }
}
```

- `service.send_timeout_seconds` 是服务处理一次发送的总时限，项目自己的读超时要比它长；`service.inbox_online_seconds` 是多久没取话（也没确认、没发心跳）就算不在线。
- `login.state`：`ok`、`expired`（登录失效，要在电脑上重新扫码）、`missing`（还没绑定）、`broken`（凭证文件读不出来）。
- 窗口没开（使用者 24 小时内没给 ClawBot 发过话，或者从没发过）时，`window.open` 是 false，`ends_at` 是 null，用量一律按 0 说，`left` 是 0。
- `quota.project.left`：一条 `normal` 的推送现在最多能拆成几条发出去。

## POST /v1/messages

发一条消息给使用者。

| 字段 | 类型 | 说明 |
|---|---|---|
| `text` | 字符串，必填 | 纯文本全文，第一行是标题。去掉首尾空白后不能为空，最多 8000 个字符；太长会被拆成几条发（每条的字数上限 2000），拆成几条就占几条额度 |
| `priority` | `urgent` / `normal` / `deferrable` | 默认 `normal`。`urgent` 不受项目上限限制；`deferrable` 在额度紧时先不发 |
| `dedupe_key` | 字符串，1 到 128 个字符 | 同一个项目 24 小时内同一个键只发一次：重复的请求拿到第一次的结果，`duplicate` 为 true。重跑任务时用，比如 `brief-2026-10-12` |
| `on_closed` | `fail` / `skip` | 默认 `fail`。对话窗口没开时：`fail` 返回 `rejected`，`skip` 安静跳过（`skipped`） |

请求里写 `to_user_id`、`context_token` 之类的字段没有用：收件人只能是绑定的使用者本人，对话由服务选。

```bash exec
curl -s -X POST "$HUB/v1/messages" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "盘前简报\n外围偏强", "dedupe_key": "brief-2026-10-12"}'
```

```json 200
{
  "status": "sent",
  "reason_code": null,
  "reason": null,
  "parts": 1,
  "parts_sent": 1,
  "duplicate": false,
  "id": "o_2f9c1a7e",
  "quota": {"left": 5, "limit": 10, "window_ends_at": "2026-10-13T10:00:00+08:00"}
}
```

同一个 `dedupe_key` 再发一次，拿到第一次的结果（`status`、`reason_code`、`reason`、`parts`、`parts_sent`、`id` 都是第一次的，`quota` 是现在的）：

```bash exec
curl -s -X POST "$HUB/v1/messages" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "盘前简报\n外围偏强", "dedupe_key": "brief-2026-10-12"}'
```

```json 200
{
  "status": "sent",
  "reason_code": null,
  "reason": null,
  "parts": 1,
  "parts_sent": 1,
  "duplicate": true,
  "id": "o_2f9c1a7e",
  "quota": {"left": 5, "limit": 10, "window_ends_at": "2026-10-13T10:00:00+08:00"}
}
```

文字是空的，请求就被拒绝，什么也没发：

### 返回

| 字段 | 说明 |
|---|---|
| `status` | 最终结果，取值见下表 |
| `reason_code` | 给程序看的稳定代码，`sent` 时是 null；全部代码见"原因代码" |
| `reason` | 给人看的中文原因，可以直接写进 Bark 的末尾；`sent` 时是 null |
| `parts` | 这条话拆成了几条 |
| `parts_sent` | 其中发出去的条数（含拿不准到没到的）。`rejected`、`failed`、`skipped` 时一定是 0 |
| `duplicate` | 是不是 `dedupe_key` 命中的重放 |
| `id` | 服务里这条发送记录的编号，排错用 |
| `quota` | 发完以后你的余量：`left` 是一条 `normal` 的推送现在最多能拆成几条，`limit` 是一个窗口总共能发几条，`window_ends_at` 是窗口什么时候关（窗口没开是 null） |

### `status` 取值和项目该怎么办

| `status` | 意思 | 微信这边算没问题吗 | 项目该怎么办 |
|---|---|---|---|
| `sent` | 全部发出去了（腾讯收下并给了编号；手机收没收到，腾讯不告诉服务） | 是 | 什么都不用做 |
| `skipped` | 窗口没开，而你带了 `on_closed: skip` | 是 | 安静跳过 |
| `unconfirmed` | 发出去了，但腾讯没有给确认（读超时、没有消息编号），**可能已经到了** | 否 | 走自己的兜底（比如 Bark），原因里说明"可能已经到了"，不要重发 |
| `partial` | 拆成几条，只发出去一部分 | 否 | 走兜底，说明发出了几条（前面发出去的可能已经到了） |
| `rejected` | 服务按规则没发：窗口没开、额度不够…… | 否 | 走兜底，把 `reason` 写进末尾 |
| `failed` | 发不出去：登录失效、腾讯拒绝、连不上…… | 否 | 走兜底，把 `reason` 写进末尾 |

## POST /v1/replies

回复使用者的一句话。用取话时给的 `reply_handle`，服务会用使用者那句话的对话回过去。

| 字段 | 类型 | 说明 |
|---|---|---|
| `handle` | 字符串，必填 | 取话时给的 `reply_handle` |
| `text` | 字符串，必填 | 同发消息 |
| `awaiting_confirmation` | 布尔 | 默认 false。回复里在问使用者要不要确认（"要平仓吗？回对确认"）就写 true，见下面"等确认" |
| `confirm_seconds` | 整数，1 到 1800 | 等确认的时间，默认 600 秒 |

返回和发消息一样。回复没有 `dedupe_key`，也永远不要自动重发。

- 句柄从使用者那句话被服务收到起 30 分钟内有效，最多回复 5 次（第 6 次是 429 `reply_limit`）；过期是 410 `handle_expired`；不是你项目的句柄、或者根本不存在，是同样的 404 `unknown_handle`。**不要把句柄存着不用超过 30 分钟。**
- 回复占的额度可以用到窗口里留给回复的那几条；窗口过期后微信不让回复，句柄也就没用了（走你自己的兜底）。
- **等确认**：回复带 `awaiting_confirmation: true`，并且至少发出了一条，服务就记下"你在等使用者确认"，记到 `confirm_seconds` 秒以后。这段时间里使用者回"对"、"是"、"确认"（不带前缀、也没有别的项目在等）会交给你，取话时 `via` 是 `confirm`。多个项目同时在等时，服务会让使用者加前缀说清楚。这句话是不是你要的确认，**由你自己判断**，不是就当普通的话处理。

先取话（取话接口在下一节细讲）。使用者在微信里发了“持仓”，项目取到它，带着 `reply_handle`：


## GET /v1/inbox

取使用者发给你项目的话。没有话就等（长轮询），一有话立刻返回。

| 查询参数 | 说明 |
|---|---|
| `wait` | 没有话时最多等几秒。0 是不等；不写取 25；超过 55 的按 55 算。负数、不是整数是 400 |
| `max` | 最多返回几条。不写取 10；超过 50 的按 50 算；**0 只是心跳**：告诉服务你还活着，不租出任何话 |

返回的每一项：

| 字段 | 说明 |
|---|---|
| `id` | 确认时用的编号 |
| `text` | 使用者的话，已经去掉了前缀。图片之类没有文字的，是空串 |
| `has_text` | 有没有文字 |
| `at`、`at_ms` | 使用者发这句话的时间（同一个时刻的两种写法） |
| `received_at` | 服务收到的时间。服务停了很久以后补收到的旧消息，`at` 会比这早很多，要不要处理由你自己判断 |
| `attempt` | 第几次交给你，第一次是 1 |
| `via` | 怎么路由到你这里的：`default`（没带前缀，你是默认项目）、`prefix`（带了你的前缀）、`confirm`（可能是对你"等确认"的回答，见上面） |
| `reply_handle` | 回复这句话用，30 分钟内有效 |

规矩：

- **租期**：取走的话，`lease_seconds`（60）秒内没有确认，服务会再给一次（`id`、`reply_handle` 不变，`attempt` 加一），最多给 5 次。所以处理一句话要**幂等**：处理两次也无害。处理完再确认，不要先确认后处理（项目挂掉会丢话）。
- **在线**：最近 90 秒内取过话、确认过或者发过心跳的项目才算在线。你不在线时使用者给你发话，服务会马上回使用者一句"『项目』现在没在线，这句话我先留着"，话留 10 分钟，你回来就能取到；超过 10 分钟作废。处理一句话可能超过 90 秒的项目，要在处理期间每隔三十秒左右发一次心跳 `GET /v1/inbox?wait=0&max=0`（Python 客户端的 `run_inbox` 替你发）。
- **一个项目一个取话循环**：同一个项目同时只能有一个在等的取话请求，新的（`wait` 大于 0）会把旧的顶掉，旧的马上返回空列表。
- 只推送的项目不能取话（403 `push_only`）。
- 前缀由使用者登记项目时定。使用者在微信里不带前缀的话归默认项目，带前缀的话（`贝塔 状态`、`贝塔：状态`）归对应的项目。

心跳（不租出话，也不会把话给别人）：

```bash exec
curl -s "$HUB/v1/inbox?wait=0&max=0" -H "Authorization: Bearer $KEY"
```

```json 200
{"items": [], "lease_seconds": 60}
```

## POST /v1/inbox/ack

确认话处理完了：以后不再给，正文立刻从服务的数据库里清掉（回复用的对话凭证留到句柄失效）。

请求体 `{"ids": ["m_…", …]}`，一次最多 50 个，超过是 400 `bad_request`（Python 客户端自己分批）。返回：

- `acked`：这次确认了几条。取走了的话，租期已过但还没被重新租出的，也算。
- `unknown`：没算数的编号——已经确认过的、过期的、作废的、别的项目的、根本不存在的，**不分是哪一种**，也不报错（确认是幂等的）。

```bash exec
curl -s -X POST "$HUB/v1/inbox/ack" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"ids\": [\"$ITEM_ID\"]}"
```

```json 200
{"acked": 1, "unknown": []}
```

再确认一次：

```bash exec
curl -s -X POST "$HUB/v1/inbox/ack" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"ids\": [\"$ITEM_ID\"]}"
```

```json 200
{"acked": 0, "unknown": ["m_9f3a1c20"]}
```

## 用错方法或路径

不存在的路径是 404 `not_found`（路径末尾多一个斜杠也是不存在，不做重定向），路径对而方法错是 405 `method_not_allowed`：

```bash exec
curl -s "$HUB/v1/messages" -H "Authorization: Bearer $KEY"
```

```json 405
{"error": {"code": "method_not_allowed", "message": "这个接口不支持这种请求方法"}}
```

不带密钥：

```bash exec
curl -s "$HUB/v1/status"
```

```json 401
{"error": {"code": "unauthorized", "message": "没带密钥，或者密钥不对：请求头里写 Authorization: Bearer <项目密钥>"}}
```

## 原因代码

发送和回复的 200 响应里，`status` 不是 `sent` 时 `reason_code` 是下表里的代码，`reason` 是对应的中文原因（`<…>` 是变量），可以直接写进 Bark 的末尾。这是**业务结果**，和下一节 HTTP 错误里的 `error.code` 是两套，互不混用。

| `reason_code` | 出现在 | `reason`（原文） |
|---|---|---|
| `never_contacted` | rejected / skipped | 还没收到你在微信里发的消息：给 ClawBot 发任意一句话就能开始接收 |
| `window_closed` | rejected / skipped | 对话窗口过期了（你最后一次发消息是 `<M月D日 HH:MM>`），给 ClawBot 发任意一句话就能恢复 |
| `quota_exhausted` | rejected | 这 24 小时的 `<10>` 条已经用完，给 ClawBot 发任意一句话就能恢复 |
| `quota_insufficient` | rejected | 这 24 小时的 `<10>` 条只剩 `<N>` 条，不够发这 `<M>` 条；给 ClawBot 发任意一句话就能恢复 |
| `project_cap` | rejected | `<项目>` 这 24 小时最多发 `<cap>` 条，已经发了 `<used>` 条，不够发这 `<M>` 条 |
| `reserved_for_others` | rejected | 剩下的 `<N>` 条是留给回复和其他项目的，这 `<M>` 条先不发 |
| `deferrable_denied` | rejected | 额度比较紧，可延后的消息先不发（还剩 `<N>` 条） |
| `too_long` | rejected | 这条要拆成 `<N>` 条，超过这个窗口最多能发的 `<M>` 条 |
| `upstream_blocked` | rejected | 腾讯拒绝了这个窗口里的发送（`<代码>`），先不再试；`<N>` 分钟后再试，或者给 ClawBot 发一句话重新开窗口 |
| `login_missing` | failed | 还没绑定微信 ClawBot：运行 hubctl login |
| `login_expired` | failed / partial | ClawBot 登录失效了：在电脑上运行 hubctl login 重新扫码 |
| `login_broken` | failed | account.json 读不出来：重新运行 hubctl login |
| `upstream_rejected` | failed / partial | 微信 ClawBot 拒绝：`<代码>` `<errmsg>` |
| `upstream_unreachable` | failed / partial | 微信 ClawBot 发送失败，重试 `<n>` 次后仍然失败：`<原因>` |
| `no_response` | unconfirmed / partial | 微信 ClawBot 没有回话，这条可能已经到了，不要重发 |
| `no_message_id` | unconfirmed / partial | 微信 ClawBot 没有返回消息编号，这条可能没有到 |
| `send_timeout` | partial / failed | 发送超过 `<N>` 秒还没发完，后面的 `<m>` 条没有发 |
| `busy` | failed | 服务正忙，这条没有发，稍后再试 |
| `interrupted` | unconfirmed | 上次发送被中断，不知道发出了几条，不要重发（只在重放去重结果时出现） |
| `duplicate_in_flight` | unconfirmed | 同一个去重键的上一次发送还没结束，先不要重发（只在重放去重结果时出现） |

拆成多条且不是全部发出时，`reason` 末尾加"；发出了 i 条，共 n 条"。原因里的登录凭证、对话凭证已经换成 `***`。

## 错误代码

非 200 的响应正文是 `{"error": {"code": "…", "message": "…"}}`，代码如下。`message` 的措辞以服务返回的为准，程序应当只看 `code`。

| HTTP | `error.code` | 什么时候 |
|---|---|---|
| 400 | `bad_request` | 请求体不是合法 JSON、字段类型不对、枚举值不认识、`dedupe_key` 长度不对、`wait` 或 `max` 不是不小于 0 的整数、`confirm_seconds` 不是 1 到 1800 的整数 |
| 400 | `empty_text` | 文字去掉首尾空白后为空 |
| 400 | `text_too_long` | 文字超过 8000 个字符 |
| 401 | `unauthorized` | 没带密钥、格式不对、认不出来（已移除的项目的密钥也一样） |
| 403 | `project_disabled` | 项目已停用，请联系运维启用 |
| 403 | `push_only` | 只推送的项目调了取话 |
| 404 | `unknown_handle` | 回复句柄不存在，或者不是你项目的 |
| 404 | `not_found` | 路径不存在 |
| 405 | `method_not_allowed` | 路径存在但用错了方法，带 `Allow` 响应头 |
| 410 | `handle_expired` | 回复句柄过期（从服务收到那句话起 30 分钟，或者那句话已经太旧、微信不能再回复） |
| 413 | `too_large` | 请求体超过 64 KiB |
| 429 | `rate_limited` | 发消息和回复每分钟请求太多，等 `Retry-After` 秒 |
| 429 | `too_many_failures` | 局域网来源认证失败太多，这个地址先停一会儿 |
| 429 | `reply_limit` | 同一个句柄的回复次数用完 |
| 500 | `internal` | 服务内部出错。发送和回复上，这条**可能已经**向腾讯发出去了，不要当作没发 |
| 503 | `shutting_down` | 服务正在关闭，这次请求什么也没发，稍后再试 |

局域网监听打开时，来源不是本机或私有网段的请求会收到正文为空的 403，不透露任何东西。

## 凭证和隐私

- 腾讯的登录凭证、对话凭证、收消息进度**不会**出现在任何响应里；回复句柄只是随机字符，和对话凭证没有任何关系。
- 服务不理解消息内容，不保存发出的和收到的正文：收到的话在你确认（或过期、作废）时立即清掉。
- 服务只向绑定的使用者本人发消息，也只认使用者本人发来的消息。
