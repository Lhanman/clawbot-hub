# 接入指南

这份指南给要用 clawbot-hub 的项目看。clawbot-hub 是家里 Mac mini 上常驻的一个服务，**只有它**登录微信 ClawBot；各个项目不再自己连腾讯，而是拿一把项目密钥，通过本机的 HTTP 接口发消息、收使用者的话。照这份指南接入，不用读服务的代码。

- Python 项目：用 `client/clawbot_hub_client.py`（一个文件，只用标准库，Python 3.9 起都能跑），下面的例子都是它的用法。
- 别的语言、shell 脚本：看 [接口文档](../api/v1.md)（`docs/api/v1.md`：`curl` 示例、每个返回字段和错误码），机器可读的描述是 `docs/api/openapi.json`；第 8 节讲用 HTTP 时要自己做到哪几件事。

## 接入要做的几件事

| 步 | 谁做 | 做什么 |
|---|---|---|
| 1 | 运维（在 Mac 上） | 登记项目，拿到密钥 |
| 2 | 项目 | 把密钥放进环境变量或不进 git 的 `.env` |
| 3 | 项目 | 把客户端文件拷进项目 |
| 4 | 项目 | 发消息，并把"微信发不出去"接到自己的 Bark 兜底上 |
| 5 | 项目（要问答的） | 起取话循环，处理使用者的话，回复，必要时等确认 |

只推送、不收话的项目做到第 4 步就够了。服务不是 Bark 的替代品：微信有微信的限制（见第 4 步），**Bark 仍然是主渠道和兜底**，微信没送到时项目要自己用 Bark 补上。

## 1. 登记项目

登记由运维在 Mac 上做，一个项目一次（完整的安装和命令见 `docs/ops/安装说明.md`）：

```bash
uv run hubctl project add my-project --guaranteed 2 --cap 4 --prefix 我的
```

- 名字：小写字母开头，2 到 32 个字符，只含小写字母、数字、减号。
- `--guaranteed`、`--cap`：保底和上限条数。微信规定使用者给 ClawBot 发一句话后 24 小时内，ClawBot 最多发 10 条（其中留 2 条给回复）；保底是别的项目动不了的条数，上限是这个项目 24 小时里最多推送的条数。所有项目的保底加上回复保留（2 条）不能超过总条数（10 条），超了登记会被拒绝。
- `--prefix`：要收话的项目必须有，使用者在微信里写“我的 状态”这样的话就交给它（见第 7 节）；只推送的项目加 `--push-only`，没有前缀，也不能取话。
- 第一个能收话的项目自动成为默认项目：使用者不带前缀的话都归它。要换默认项目，加 `--default`。
- 不是默认项目的项目，发出的消息第一行前面会自动加上 `【标签】`（标签默认是前缀，只推送的项目是名字；可以用 `--label` 改、`--no-label` 去掉）。**项目不要自己加标签。**
- 密钥（`chub_` 开头）**只显示一次**，登记完马上存好；丢了只能 `hubctl project rotate` 换一把。

## 2. 放好密钥

- 放进环境变量 `CLAWBOT_HUB_KEY`，或者项目自己的 `.env`（确认 `.env` 在 `.gitignore` 里，**不进 git**；仓库是公开的也一样，别把密钥写进代码、日志、报错和文档）。
- 客户端自己只读环境变量（默认 `CLAWBOT_HUB_KEY`，用 `key_env=` 可以换名字），不读任何文件。`.env` 由项目自己读进环境变量，或者读出来以后用 `HubClient(key=…)` 传给它。`repr` 和日志里不出现密钥。
- 服务的地址默认是 `http://127.0.0.1:8790`（服务和项目在同一台机器上）。服务和项目不在同一台机器时，见 `docs/ops/安装说明.md` 的“局域网监听”（密钥在局域网里是明文走的），然后用 `HubClient("http://<地址>:<端口>")`。

## 3. 拿到客户端

把仓库里的 `client/clawbot_hub_client.py` 整个文件拷进自己的项目里（放哪都行，别改它；要改先和服务这边说）。它只用标准库，不用 `pip install` 任何东西。

```python
from clawbot_hub_client import HubClient

hub = HubClient()  # 密钥读环境变量 CLAWBOT_HUB_KEY，地址默认 http://127.0.0.1:8790
print(hub.health())  # 探活，不要密钥：{"ok": True, "version": "…", "api": "1"}
print(hub.status()["quota"]["project"])  # 你项目自己的额度
```

客户端文件里的 `API_VERSION` 是它按哪一版接口写的，服务的 `health()["api"]` 是服务现在的接口版本；项目想在启动时核对的话，比较这两个字符串。

## 4. 发消息，微信发不出去就走 Bark

```python
from clawbot_hub_client import HubClient, HubError, HubUnavailable

hub = HubClient()


def push(text: str, dedupe_key: str) -> None:
    """推送一条消息：先发微信；微信没送到，就走 Bark，并把原因写在 Bark 的末尾。"""
    why = None  # 微信这边出了什么问题；None 表示没问题
    try:
        result = hub.send(text, dedupe_key=dedupe_key)
    except HubUnavailable as exc:  # 服务连不上、读超时、回了 5xx
        why = f"微信服务不可用：{exc.message}"
        if exc.possibly_sent:
            why += "（这条可能已经到了，别重发）"
    except HubError as exc:  # 密钥不对、项目被停用、请求写错了：接入的毛病，但消息不能丢
        why = f"微信服务拒绝了请求：{exc.message}"
    else:
        if result.needs_fallback:
            why = result.reason or result.status
            if result.maybe_delivered:
                why += "（这条可能已经到了，别重发）"
    if why is not None:
        send_bark(text + f"\n\n微信没发出去：{why}")  # send_bark 是项目原来就有的 Bark 推送
```

`hub.send()` 是**同步**的：服务发完（或确定发不出去）才返回，拿到的就是最终结果。结果分两类，别混：

| 返回 | 微信这边算没问题吗 | 项目该怎么办 |
|---|---|---|
| `sent` | 是 | 什么都不用做 |
| `skipped` | 是（你带了 `on_closed="skip"`，窗口没开就算了） | 安静跳过 |
| `unconfirmed` | 否：发出去了但腾讯没确认，**可能已经到了** | 走 Bark，原因里写明可能已经到了，不要重发 |
| `partial` | 否：拆成几条，只发出去一部分，前面的**可能已经到了** | 走 Bark，原因里写明发出了几条 |
| `rejected` | 否：服务按规则没发（窗口没开、额度不够……） | 走 Bark，把 `reason` 写进末尾 |
| `failed` | 否：发不出去（登录失效、腾讯拒绝、连不上……） | 走 Bark，把 `reason` 写进末尾 |
| 抛 `HubUnavailable` | 否：服务连不上、读超时、5xx | 走 Bark；`possibly_sent` 为真时（读超时、连接被重置、500）写明可能已经到了 |
| 抛 `HubAuthError`、`HubRequestError` | 否：密钥不对、项目被停用、请求写错了 | 重试没有用；消息也走 Bark，并且让人知道（日志、告警），这是要人处理的毛病 |

`SendResult` 上的三个属性已经把这张表算好了：`ok`（`sent`、`skipped`）、`needs_fallback`（不是 `ok`，服务以后加了客户端不认识的状态也算）、`maybe_delivered`（`unconfirmed`、`partial`）。`reason` 是给人看的中文原因，可以直接写进 Bark；`reason_code` 是给程序看的稳定代码（全部代码见接口文档的“原因代码”）。

几条实用的规矩：

- **用稳定的 `dedupe_key`。** 键由“这是哪一次推送”决定，不要用时间戳或随机数：当天的盘前简报永远是 `brief-2026-10-12`。这样脚本重跑、人工补发都不会让使用者收到两份——同一个键 24 小时内只发一次，重复的请求拿到第一次的结果（`duplicate` 为 true）。
- **不会偷偷重发。** 读超时、连接被重置、500 这几种“可能已经发出去了”的情形，客户端和服务都不重发，由项目自己决定；只有给了 `dedupe_key`、并且确定请求没被处理（连不上、502、503、504）时，客户端才重试一次。
- **写短一点。** 第一行是标题；一条消息最多 8000 个字符，超过 2000 个字符会拆成几条，**拆成几条就占几条额度**。长报告发摘要，全文放别处。
- **可有可无的消息**用 `on_closed="skip"`（窗口没开就安静跳过），额度紧时可以先不发的用 `priority="deferrable"`，止损之类一定要发的用 `priority="urgent"`（不受项目上限限制）。
- **回复使用者的话**可以用到窗口里留给回复的那几条（默认 2 条），推送动不了这几条；回复本身不受项目保底和上限的限制。查额度：`hub.status()["quota"]["project"]["left"]` 是一条 `normal` 的推送现在最多能拆成几条。
- 窗口没开（使用者 24 小时没给 ClawBot 发过话）时，微信不让主动发：结果是 `rejected`，`reason_code` 是 `window_closed`，原因里已经写了怎么恢复（给 ClawBot 发任意一句话）。所以每天看完简报随手回一句，是最省事的办法。

## 5. 取话：收使用者的话、回复、等确认

要问答的项目起一个取话循环。`run_inbox` 替你做了“至少送达一次”需要的全部事情：

```python
import threading

from clawbot_hub_client import HubClient, HubError, Inbound

hub = HubClient()
stop = threading.Event()


def answer(item: Inbound, text: str, confirm: bool = False) -> None:
    """回复这句话；回复没发出去也走 Bark，但不要让它抛异常（抛了这句话会被再处理一次）。"""
    try:
        result = hub.reply(item.reply_handle, text, awaiting_confirmation=confirm)
    except HubError as exc:
        why = exc.message
    else:
        why = result.reason if result.needs_fallback else None
    if why is not None:
        send_bark(text + f"\n\n微信没发出去：{why}")


def handle(item: Inbound) -> None:
    """处理使用者的一句话。没确认的话服务会再给一次，所以这里要幂等：处理两次也无害。"""
    if already_done(item.id):  # 项目自己记，比如记在数据库里
        return
    if item.via == "confirm" and pending_confirmation():
        # 使用者回了“对”之类：是不是你上一条回复在等的确认，由你自己判断
        run_confirmed_action()
        answer(item, "已执行")
        return
    if item.text.startswith("平仓"):
        remember_pending_confirmation(item.text)
        answer(item, "要平仓吗？回“对”确认", confirm=True)
        return
    answer(item, handle_command(item.text))  # handle_command：项目自己的指令解析


hub.run_inbox(handle, stop=stop.is_set)  # 一直跑，直到 stop 被置位；每个项目只起一个
```

`run_inbox` 的行为（细节在 `clawbot_hub_client.py` 的文档字符串里）：

- 取话是长轮询，没有话就等（默认最多 25 秒），一有话立刻返回。对每一句调用 `handle(item)`；**`handle` 正常返回才算处理完**，整批处理完统一确认；`handle` 抛异常的那一句不确认，租期（60 秒）过后服务会再给一次（`id` 不变，`attempt` 加一），最多给 5 次。所以先处理、后确认，处理要**幂等**。
- `handle` 运行期间，后台线程每隔 `online_seconds`（服务认为项目在线的时长，默认 90 秒）的三分之一发一次**心跳**，处理一句慢指令超过 90 秒也不会被判成没在线。
- 连不上服务时退避：5 秒起每次翻倍，最多 60 秒；服务回 429 就睡 `Retry-After` 秒；密钥不对或项目被停用（`HubAuthError`）直接抛出，不要无限重试。
- `stop()` 为真时当前这一批处理完并确认，然后返回。

使用者的话怎么到你这里：

- 不带前缀的话归默认项目；带前缀的话（“我的 状态”、“我的：状态”）归对应的项目，交给你的 `item.text` 已经去掉了前缀。`item.via` 告诉你是怎么路由来的：`default`、`prefix`，或者 `confirm`。
- 你不在线（90 秒内没取过话、没确认过、没发过心跳）时使用者给你发话，服务会马上回使用者一句“现在没在线，这句话我先留着”，话留 10 分钟，你回来就能取到。
- `item.at` 是使用者发这句话的时间，`item.received_at` 是服务收到的时间。服务停了很久以后补收到的旧消息，`at` 会比 `received_at` 早很多，要不要处理由你自己判断。

**回复**用取话给的 `item.reply_handle`，服务会用使用者那句话的对话回过去：

- 句柄从服务收到那句话起 **30 分钟**内有效，同一个句柄最多回复 5 次；过期是 `HubRequestError`（`code` 是 `handle_expired`）。**不要把句柄存着不用超过 30 分钟。**
- **需要使用者确认的回复**（“要平仓吗？回对确认”）带 `awaiting_confirmation=True`（可以用 `confirm_seconds` 指定等多久，默认 600 秒）。这段时间里使用者回“对”、“是”、“确认”（不带前缀、也没有别的项目在等）会交给你，`item.via` 是 `confirm`。多个项目同时在等时，服务会让使用者加前缀说清楚。
- `via` 是 `confirm` 的话，**是不是你要的确认由你自己判断**：服务只知道这句话正好是个确认词、而你在等确认，不知道它是不是对你那个问题的回答。不是你要的，就当普通话处理（上面的例子里 `pending_confirmation()` 为假时就往下走）。服务重启不清掉“在等确认”的记录；项目自己记的待确认事项如果只在内存里，项目重启就丢了——这时使用者回“对”会交给项目，项目回一句“没有等你确认的事”就行。

自己写取话循环、不用 `run_inbox` 的项目要自己做到这些：处理一句话可能超过 `online_seconds` 时，处理期间每隔三十秒左右发一次心跳 `GET /v1/inbox?wait=0&max=0`（只让服务知道你还活着，不租出话）；**每个项目同一时间只能有一个取话循环**，同时起两个，新的会把旧的顶掉。

## 6. 对接约定

这几条是服务和各个项目之间的约定，接入时逐条对一遍：

1. `sent`、`skipped` 算微信这边没问题；`unconfirmed`、`partial`、`rejected`、`failed` 以及 `HubUnavailable` 都走 Bark，并把 `reason` 写进 Bark 的末尾，格式是“微信没发出去：……”（和 ashare-quant 现在的写法一样）。
2. `unconfirmed`、`partial` 和 `HubUnavailable(possibly_sent=True)` 的原因里要说明“可能已经到了”，不要重发。
3. 推送用稳定的 `dedupe_key`（比如 `brief-2026-10-12`），重跑不会发两份。
4. 取话处理要幂等；回复用取话给的句柄；需要等使用者确认的回复带 `awaiting_confirmation=True`；`via` 是 `confirm` 的话，由项目自己判断这句话是不是它要的确认，不是就当普通话处理。
5. 处理一句话可能超过 `online_seconds`（默认 90 秒）的项目用 `run_inbox`（它会发心跳）；自己写取话循环的项目要自己发心跳；每个项目同一时间只能有一个取话循环。
6. 取话的前缀由使用者在登记时定；服务分不清默认项目自己的指令里有没有和别的项目前缀同名的词，登记前缀时请自己确认（见第 7 节）。
7. **不要自己向使用者的微信发任何别的东西**（不要自己登录 ClawBot、不要绕过服务直连腾讯）：服务是唯一登录 ClawBot、唯一和腾讯说话的程序，额度和登录状态都由它统一管，项目绕过它自己发，服务就算不准额度，还可能影响它的登录。也不要保存回复句柄超过 30 分钟。
8. 建议不要把密钥、使用者的话、回复的内容写进日志和报错里（服务那边不保存发出的和收到的正文，客户端的日志里也没有它们）。

## 7. 前缀怎么取

前缀由使用者（运维）在 `hubctl project add --prefix` 时定，项目只是接受它。取的时候注意：

- 1 到 8 个字符，只含字母、数字、汉字，英文不分大小写；不能和别的项目的前缀重复，不能是“服务”（服务自己的指令词）和“对”“是”“确认”（确认词）。
- 前缀要出现在句首，后面紧跟空格、冒号或逗号才算（“我的 状态”、“我的：状态”）；“我的因子”这样前缀后面直接连着字的，**不算**带前缀，原样交给默认项目。
- **服务分不清默认项目自己的指令里有没有和别的项目前缀同名的词。** 比如别的项目的前缀取了“状态”，默认项目整句“状态”就会被交给那个项目。登记前缀时请自己确认：默认项目现有的全部指令词里，没有哪个和新前缀同名（登记命令的输出里也会提醒这一点）。

使用者随时可以在微信里发“服务 项目”看有哪些项目、哪个是默认、在不在线；发“服务 状态”看登录状态、窗口剩余时间和已用条数。

## 8. 不用 Python 的项目

照 [接口文档](../api/v1.md) 的 `curl` 示例用 HTTP 就行。客户端替 Python 项目做了下面这些事，换语言时要自己做到：

- 每个请求带 `Authorization: Bearer <项目密钥>`；非 200 的返回正文是 `{"error": {"code": …, "message": …}}`，只看 `code`。
- 发消息和回复**不要**在读超时、连接被重置、500 之后重发（消息可能已经到了）；给了 `dedupe_key` 的推送，只在确定没被处理（连不上、502、503、504）时才重试。读超时要比服务的发送总时限长（`GET /v1/status` 里的 `service.send_timeout_seconds`，默认 30 秒，读超时取 35 秒以上）；取话的读超时要比 `wait` 长 10 秒以上。
- 取话循环：先处理、后确认（`POST /v1/inbox/ack`，一次最多 50 个 `id`）；连不上时退避 5、10、20……最多 60 秒；429 睡 `Retry-After` 秒；处理期间发心跳。
- 把返回的 `status` 按第 4 步那张表接到自己的 Bark 兜底上。

shell 脚本、cron 任务：用 `curl`（接口文档里的示例），或者服务这边的 `hubctl send`（在服务的仓库目录里运行，或者 `uv run --project <服务的仓库目录> hubctl send …`），它就是给脚本用的，退出码说明了结果（0 是发了或安静跳过，3 未确认，4 只发了一部分，5 被拒绝，6 失败，10 没发出去，11 密钥不对，12 其他接口错误，13 可能已发出）：

```bash
uv run hubctl send "夜间备份完成" --dedupe-key "backup-$(date +%F)" --on-closed skip --key-env CLAWBOT_HUB_KEY
```

非 0 就走自己的 Bark；3、4、13 的原因里要写明可能已经到了。

## 9. 出了问题怎么查

| 现象 | 多半是 | 怎么办 |
|---|---|---|
| `HubAuthError`，401 `unauthorized` | 密钥写错了，或者项目已被移除 | 核对环境变量；运维 `uv run hubctl project list --all` 看，需要的话 `hubctl project rotate` 换一把 |
| `HubAuthError`，403 `project_disabled` | 项目被停用了 | 运维 `hubctl project enable` |
| `HubAuthError`，403 `push_only` | 只推送的项目调了取话 | 只推送的项目不能取话（登记后不能改，要改用新名字重新登记） |
| `rejected` / `window_closed`、`never_contacted` | 使用者 24 小时没给 ClawBot 发过话 | 给 ClawBot 发任意一句话；这条走了 Bark |
| `rejected` / `project_cap`、`reserved_for_others`、`quota_*` | 这个窗口的额度用完了 | 写短一点；看 `hub.status()` 里的额度；必要时运维 `hubctl project set` 调保底和上限 |
| `failed` / `login_expired` | ClawBot 登录失效了 | 运维在电脑上 `hubctl login` 重新扫码（服务会用 Bark 通知运维） |
| `HubRequestError`，`handle_expired` | 回复晚了，句柄超过 30 分钟 | 走 Bark，下次尽快回复 |
| 使用者的话没到项目 | 前缀不对、项目没起取话循环，或者话被路由给了别的项目 | 在微信里发“服务 项目”看谁在线、谁是默认；`uv run hubctl status` 看队列 |
| 话被处理了两次 | `handle` 没返回就抛了异常，或者没在租期内处理完 | 处理要幂等，用 `item.id` 去重 |

服务这边的全貌：`uv run hubctl status`（服务、登录、窗口、各项目的在线和用量），`uv run hubctl events --kind send` 看最近的发送记录（只有结果，没有正文）。项目这边：`hub.status()` 是你项目自己的额度和全局的登录、窗口状态。

没有真的微信时怎么测自己的接入：把 `HubClient` 当参数传进你的推送函数，测试里换成假的；想对着真服务演练，用 `docs/ops/安装说明.md` 的“演练”（独立运行的假腾讯加另一个数据目录和端口），不要拿真的 ClawBot 试。
