# 回退手册

服务出问题时怎么办：让项目退回直连、或者只用 Bark，以及怎么从备份里恢复。

## 总原则

1. **先停服务，保留现场。** 停服务一律 `launchctl bootout gui/$(id -u)/com.clawbot-hub.serve`。别急着删日志、删数据库——事后要靠它们查原因。要清理就「移走」，不要「删掉」。
2. **Bark 不经过服务。** 各项目自己发 Bark，服务挂了、停了都不影响它。所以最坏的情况也只是「微信这一路没了」，重要的通知还有 Bark。
3. **只要中间没有重新扫过码，备份的凭证就还有效。** 重新扫码会让旧凭证作废，所以遇到问题先别急着扫码。
4. **备份里有登录凭证**，恢复、复制时都别放进云盘或 git，用完妥善处理。

本手册里所有「停服务」都是这一条命令：

```
launchctl bootout gui/$(id -u)/com.clawbot-hub.serve
```

预期：没有输出；`uv run hubctl status` 第一行是「服务：没有在运行」。

## 先判断是哪一种

| 现象 | 去哪一节 |
|---|---|
| 想退回迁移之前的样子（ashare-quant 自己连腾讯） | A |
| 服务不稳定，但先不想动项目那边，只要重要通知别丢 | B |
| 数据库坏了、配置改乱了、项目被误删了 | C |
| 升级之后出问题 | D |
| 提示登录已失效 | E（这不是回退，重新扫码） |
| 磁盘满了、备份失败 | F |

## A. 退回直连（ashare-quant 回到 direct）

适用：迁移之后发现微信这条路不对劲，想让 ashare-quant 回到自己直连腾讯。前提：迁移以后**没有重新扫过码**，并且第 3 步备份的凭证文件还在。

1. 停服务：`launchctl bootout gui/$(id -u)/com.clawbot-hub.serve`。预期：`hubctl status` 第一行是「服务：没有在运行」。
2. 停 ashare-quant 的微信问答：`launchctl bootout gui/$(id -u)/com.ashare-quant.wechat`（它现在是服务的客户端，先停掉再改）。
3. 把 ashare-quant 的微信模式改回 `direct`。
4. 把备份的凭证放回去：

   ```
   cp -p ~/clawbot-credentials-backup-<日期>.json "<ashare-quant 目录>/data/notify/clawbot.json"
   chmod 600 "<ashare-quant 目录>/data/notify/clawbot.json"
   ```

5. 启动 ashare-quant 的微信问答：`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.ashare-quant.wechat.plist`。
6. 验证：手机微信给 ClawBot 发一句「状态」，几秒内收到回复；`uv run aq brief --push` 微信和 Bark 都收到。

注意这几件事：

- 备份里是**切换那一刻**的收消息进度（`updates_buf`）。服务在这段时间收过的消息，退回后可能被重新收到一遍（带旧进度再收会不会重发，要真机验证，见《真机验证清单》里的 `test_old_buf_redelivers`）。看到重复的话不用慌，忽略即可。
- 服务这段时间用掉的条数不在备份里：ashare-quant 直连后按它自己的记录算，会比实际用的少。窗口里的真实数字可以在退回之前看一眼 `hubctl status`（服务的数据库里有）。如果被腾讯拒绝了，ashare-quant 会自己走 Bark。
- **如果迁移之后重新扫过码**，备份的凭证已经作废，不能这样退。要退的话在 ashare-quant 里 `aq wechat login` 重新扫一次码（服务那边的登录会因此失效，反正它已经停了）。

## B. 只用 Bark（服务停着，项目那边先不动）

适用：服务不稳定，但你还没决定要不要退回，只要重要通知别丢。

1. 停服务：`launchctl bootout gui/$(id -u)/com.clawbot-hub.serve`。不要用 `kill` 或 `launchctl stop`，它们不会让 launchd 记住「你想让它停着」。
2. 就这样。各项目连不上服务时（客户端抛 `HubUnavailable`，`hubctl send` 退出码 10）会自己走 Bark：ashare-quant 的渠道逻辑是「微信发不出去，Bark 末尾写原因」。
3. 代价：这期间微信问答收不到你的话（没人收），推送只有 Bark。

想恢复：`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.clawbot-hub.serve.plist`，然后 `hubctl doctor`、`hubctl status`。窗口是腾讯那边按你最后一次发话算的，服务停着不会让它多过期一秒；停得久了，在微信里给 ClawBot 发一句话就重新开了。

## C. 从备份恢复

适用：`hubctl doctor` 说数据库打不开或 `integrity_check` 不是 ok、配置改乱了、项目被误删了。

备份在 `<数据目录>/backups/` 下（默认 `~/.clawbot-hub/backups/`），名字分三种：

| 名字 | 是什么 |
|---|---|
| `auto-<时间>` | 服务每天 04:00 自动做的，保留最近 14 份 |
| `pre-upgrade-v<旧版本>-v<新版本>-<时间>` | 升级数据库之前自动做的，不会被自动清理 |
| `<时间>` | 手动 `hubctl backup` 做的，不会被自动清理 |

每份备份里有 `hub.db`、`account.json`、`config.yaml`、`bark.json`（有几个算几个）。

恢复步骤：

1. 停服务：`launchctl bootout gui/$(id -u)/com.clawbot-hub.serve`。
2. 选一份备份：`ls -1 ~/.clawbot-hub/backups/`。
3. **先把现在的文件移走，不要覆盖：**

   ```
   mkdir ~/.clawbot-hub.before-restore-$(date +%Y%m%d)
   cd ~/.clawbot-hub
   mv hub.db hub.db-wal hub.db-shm ~/.clawbot-hub.before-restore-$(date +%Y%m%d)/ 2>/dev/null
   ```

   `hub.db-wal`、`hub.db-shm` 一定要一起移走：旧的 `-wal` 配上新放回去的 `hub.db` 会把库搞坏。
4. 把备份里的数据库放回来（`<备份>` 换成第 2 步选的目录名）：

   ```
   cp -p ~/.clawbot-hub/backups/<备份>/hub.db ~/.clawbot-hub/hub.db
   chmod 600 ~/.clawbot-hub/hub.db
   ```

5. `account.json`、`config.yaml`、`bark.json` 只在需要时才一起恢复，**先看现在的有没有比备份新**：如果备份之后重新扫过码，现在的 `account.json` 才是有效的，别用旧的覆盖它。要恢复的话同样先移走现有的，再 `cp -p` 回来，`chmod 600`。
6. 启动服务，检查：

   ```
   launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.clawbot-hub.serve.plist
   uv run hubctl doctor
   uv run hubctl status
   ```

   预期：`doctor` 没有 ✗；`status` 里项目、窗口、已用条数是备份那一刻的样子。

恢复的是**备份那一刻**的状态，要有心理准备：

- 备份之后登记的项目会没有（密钥只存摘要，也找不回来，只能重新登记并换密钥）；
- 备份之后的发送记录、事件没有了；窗口里的已用条数可能比实际少，直到下一个窗口；
- 不确定备份是不是最近的，先 `hubctl backup` 把现在的状态也备一份，再恢复。

## D. 升级之后出问题

升级会自动迁移数据库，**数据库比程序新时旧程序会拒绝启动**（退出码 3），所以不能只把代码退回去，要连数据库一起退到升级前。

1. 停服务：`launchctl bootout gui/$(id -u)/com.clawbot-hub.serve`。
2. 找升级前的备份：`ls -1 ~/.clawbot-hub/backups/ | grep pre-upgrade`，名字里 `v<旧>-v<新>` 就是数据库版本的变化。
3. 按 C 的步骤把那份备份里的 `hub.db` 恢复回来（`account.json` 通常不用动）。
4. 把代码退回升级前的版本：`cd ~/workbench/clawbot-hub && git log --oneline | head` 找到升级前的提交，`git checkout <提交>`，再 `uv sync`。
5. 启动服务，`hubctl doctor`。

查清楚原因、修好以后，再 `git checkout main && git pull && uv sync` 重新升级。

## E. 登录失效（不是回退）

`hubctl status` 说登录已失效、手机收到「登录失效」的 Bark：在电脑上 `uv run hubctl login` 重新扫码。服务在 5 秒内自动换上新凭证，不用重启，也会发一条「登录已恢复」。

## F. 磁盘满了、备份失败

手机收到「备份失败」的 Bark，或者 `hubctl doctor` 报磁盘不足：先腾出空间（`~/.clawbot-hub.*` 里移走的旧目录、旧备份），再手动 `uv run hubctl backup`，成功了就没事。

## 退回之后

- 把原因记下来：`uv run hubctl events --limit 100`、`~/.clawbot-hub/logs/hub.log` 里出事那段，贴给开发的人（里面没有消息正文和凭证）。
- 查清楚之前，别删数据目录、别重新扫码。
- 想重新迁移时，从《迁移手册》第 1 步重来（先检查数据目录是不是干净）。
