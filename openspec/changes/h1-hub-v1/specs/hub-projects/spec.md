# Spec Delta

## Purpose

规定怎么让一个项目用上这个服务：登记一次（名字、密钥、前缀、保底和上限条数），之后只靠密钥通信；一个项目出问题或密钥泄露，一条命令就能断开它；项目之间互相看不到对方的东西。服务只认密钥，不管项目用什么语言、在哪个仓库、跑在哪里。

管理命令（`hubctl project …`）直接改数据库，服务每处理一个请求都读库里最新的项目设置、不缓存，所以改动对下一个请求立即生效，不用重启服务。检查和写入在同一个写事务里，两条命令同时登记也不会一起超过保底总数。

## ADDED Requirements

### Requirement: 登记项目

`hubctl project add <名字> [--prefix <前缀>] --guaranteed <条> --cap <条> [--default [--yes]] [--label <标签> | --no-label] [--push-only]` MUST 登记一个项目并**只打印一次**它的密钥。校验：

- **名字**：`^[a-z][a-z0-9-]{1,31}$`；不能与已有的项目（含已移除的）重名。`_hub`、`_import` 是服务内部保留的名字（见"服务内部的两个名字"），上面的规则本来就不允许下划线开头。
- **前缀**：能收话的项目 MUST 有前缀，缺了报错"需要收话的项目必须有前缀"；只推送的项目没有前缀。前缀 1 到 8 个字符，只含字母、数字、汉字，英文不分大小写（比较前先做 NFKC 规范化和小写）；不能与别的项目（含已停用的，不含已移除的）的前缀重复；不能是 `hub.label`（默认"服务"，服务自己的指令词）；不能是 `routing.confirm_words` 里的词（见 `hub-inbox`，默认对、是、确认）。前缀不含空白和标点，所以任何一句话最多命中一个前缀。
- **保底、上限**：整数，`0 ≤ 保底 ≤ 上限 ≤ 窗口总条数 − 回复保留`（`quota.window_limit − quota.reply_reserve`）；所有启用的项目的保底之和加上回复保留 MUST 不超过窗口总条数，超了就拒绝并列出现在每个项目的保底。
- **默认项目**：同一时间最多一个，不能是只推送的项目。第一个登记的**能收话**的项目自动成为默认项目；之后加 `--default` 才把默认换成它，这会换掉原来的默认项目，是需要确认的操作（`--yes`，确认的规矩见 `hub-cli`），输出写明原来的默认项目是谁。
- **标签**：回复和推送的第一行前面加的 `【标签】`（见 `hub-send`）。标签 1 到 16 个字符，不含换行和 `【` `】`，不能是 `hub.label`。登记时 MUST 把标签落成具体的值存下来：`--label` 给了就用它；`--no-label` 就没有标签；两个都没给：默认项目没有标签（现在的用法一个字都不用变），其他能收话的项目用前缀，只推送的项目用名字（名字超过 16 个字符的取前 16 个；这样得出的标签恰好等于 `hub.label` 的，登记被拒绝，提示用 `--label` 另取一个）。之后换默认项目不改任何项目的标签。
- **只推送**（`--push-only`）：只发消息、不取话的项目。不能有前缀，不能是默认项目；调用取话接口得到 403 `push_only`。是不是只推送登记后不能改（要改就用新名字重新登记）。
- **称呼**：服务对使用者提到一个项目（离线提醒、"有几个项目在等你确认"、`服务 项目`）时统一用它的前缀，没有前缀用名字。

登记成功时输出 MUST 多带一行提醒：服务分不清默认项目自己的指令里有没有和这个前缀同名的词（例如前缀取"状态"，默认项目整句"状态"就会被交给这个项目），请自己确认。

#### Scenario: 第一个项目成为默认项目

- **WHEN** 登记第一个项目 `ashare-quant`，前缀 `量化`，保底 6，上限 8
- **THEN** 打印一次密钥（`chub_` 开头），`hubctl project list` 里它是默认项目，没有标签

#### Scenario: 只推送的项目不当默认项目

- **WHEN** 先登记 `--push-only` 的 `cron-job`，再登记有前缀的 `x`
- **THEN** 登记 `cron-job` 时没有默认项目，它的标签是名字 `cron-job`；`x` 登记后自动成为默认项目；同时给 `--push-only` 和 `--default` 被拒绝，说明只推送的项目不能当默认项目

#### Scenario: 总保底超了

- **WHEN** 窗口总条数 10、回复保留 2，已有项目保底 6，再登记一个保底 4 的项目
- **THEN** 拒绝，提示"保底合计 10 加上回复保留 2 超过窗口总条数 10"，并列出现有各项目的保底；没有新增项目

#### Scenario: 上限不能超过窗口减回复保留

- **WHEN** 窗口总条数 10、回复保留 2，登记上限 9 的项目；再登记保底 5、上限 4 的项目
- **THEN** 两次都拒绝：前一次提示上限最多 8，后一次提示保底不能大于上限

#### Scenario: 名字不合规或重名

- **WHEN** 登记名字 `Ashare`、`1x`、`a`、`_hub`，或者与一个已移除的项目同名
- **THEN** 都拒绝，各自说明原因

#### Scenario: 前缀重复

- **WHEN** 登记前缀 `X` 的项目，已有一个前缀 `x` 的项目（或已停用的项目占着这个前缀）
- **THEN** 拒绝，提示前缀已被谁占用

#### Scenario: 前缀不合规

- **WHEN** 前缀是 `服务`、`对`，或者 9 个字、含空格或标点
- **THEN** 都拒绝，各自说明原因；`hub.label` 改成"助手"以后，前缀 `助手` 被拒绝，`服务` 可以用

#### Scenario: 能收话的项目必须有前缀

- **WHEN** 登记一个没有 `--prefix` 也没有 `--push-only` 的项目
- **THEN** 拒绝，提示"需要收话的项目必须有前缀"；没有新增项目

#### Scenario: 只推送项目不能有前缀

- **WHEN** 登记 `--push-only` 同时给了 `--prefix`
- **THEN** 拒绝，说明只推送的项目没有前缀

#### Scenario: 换默认项目要确认

- **WHEN** 已有默认项目 A，在非终端环境登记 B 并带 `--default` 但没带 `--yes`；再带上 `--yes` 登记
- **THEN** 前者拒绝（退出码 2）、没有新增项目；后者成功，输出写明"原来的默认项目是 A"，之后 B 是默认项目、A 不再是；A 和 B 的标签都没变

#### Scenario: 标签的规则

- **WHEN** 依次登记：前缀 `a` 的默认项目 A（没给标签）、前缀 `x` 的项目 B（没给标签）、前缀 `y` 的项目 B2（`--no-label`）、前缀 `z` 的项目 B3（`--label 备用`）、只推送的项目 `cron-job`（没给标签）、只推送的项目 `weekly-report-generator`（23 个字符，没给标签）
- **THEN** 标签依次是：无、`x`、无、`备用`、`cron-job`、`weekly-report-ge`（名字的前 16 个字符）；标签含 `【`、超过 16 个字、或者等于 `hub.label` 的登记被拒绝

#### Scenario: 换默认项目不改标签

- **WHEN** A（默认、无标签）和 B（标签 `x`）已登记，执行 `project set B --default --yes`
- **THEN** B 成为默认项目、A 不再是；A 的标签仍是无，B 的标签仍是 `x`；之后给 A 发的推送不带标签、给 B 发的仍带 `【x】`

#### Scenario: 前缀可能撞上默认项目的指令

- **WHEN** 成功登记一个前缀为 `状态` 的项目
- **THEN** 输出里有一行提醒，说明默认项目整句"状态"会被交给这个项目

### Requirement: 服务内部的两个名字

数据库初始化时 MUST 预置两个内部项目：`_hub`（服务自己的回复记在它名下）和 `_import`（`hubctl import-credentials` 带进来的已用条数记在它名下，类别是"推送"，不动回复保留）。它们没有可用的密钥（占位的摘要永远不会匹配）、不是启用的项目、保底和上限都是 0。它们 MUST NOT 出现在任何列表（`hubctl project list`、`服务 项目`、状态页）、路由、保底合计和默认项目的候选里；用量只算进窗口总已用（`_hub` 的回复同时算进回复已用），见 `hub-quota`。

#### Scenario: 内部名字不露面

- **WHEN** 数据库刚建好，执行 `hubctl project list`、`hubctl project list --all`，再让服务回复一次"服务 项目"
- **THEN** 列表和回复里都没有 `_hub`、`_import`；登记第一个项目时它仍然自动成为默认项目；保底合计不含它们

#### Scenario: 内部名字不能登录

- **WHEN** 任何字符串当密钥请求 `GET /v1/status`，包括数据库里占位的摘要的各种猜测
- **THEN** 都是 401 `unauthorized`，请求里不可能认成 `_hub` 或 `_import`

### Requirement: 项目密钥

密钥 MUST 是 `chub_` 加 43 个 URL 安全的 base64 字符（`secrets.token_urlsafe(32)`，32 字节随机数）。数据库里 MUST 只存它的 SHA-256 摘要，不存原文；密钥只在登记和换钥时向标准输出显示一次（这是 `hub-cli` 里"输出不含密钥"的唯一例外，它不进日志、不进事件记录）。所有接口 MUST 从请求头 `Authorization: Bearer <密钥>` 认项目，先按摘要查、再用恒定时间比较。

- 没带、格式不对、认不出来、已移除项目的密钥：401 `unauthorized`，返回内容完全一样，不透露是哪一种。
- 项目已停用：403 `project_disabled`。
- 认证失败的限流只对**局域网来源**生效：来源地址（TCP 对端地址，不看任何请求头）是 127.0.0.0/8 或 `::1` 的请求不计入、也不受限制（本机的进程本来就能读数据目录）。局域网来源的地址 1 分钟内认证失败 10 次（固定值），之后来自这个地址的请求在认证之前就被拒绝：429 `too_many_failures`，带整数的 `Retry-After`（距离最早一次失败满 1 分钟还要几秒，至少 1）。被 429 拒绝的请求 MUST NOT 再计入失败，所以过了 1 分钟没有新的失败，这个地址就恢复。
- 日志里只出现项目名，不出现密钥或密钥的任何一段。

`hubctl project rotate <名字> [--grace <分钟>]` 生成新密钥（打印一次，是需要确认的操作），旧密钥立刻失效；`--grace` 让旧密钥再用若干分钟（0 到 60，默认 0），给项目换配置留时间。宽限期内又换一次钥，更早的旧密钥立刻失效，只保留上一把。

#### Scenario: 错误的密钥

- **WHEN** 用一把没登记过的密钥调 `GET /v1/status`
- **THEN** 401 `unauthorized`，正文是 `{"error": {"code": "unauthorized", …}}`；用一个已停用项目的密钥得到的是 403 `project_disabled`；用一个已移除项目的密钥得到的是 401，和没登记过的一样

#### Scenario: 密钥的格式

- **WHEN** 登记一个项目
- **THEN** 打印的密钥以 `chub_` 开头、总长 48 个字符、后 43 个字符只含字母数字和 `-` `_`；用这把密钥请求 `GET /v1/status` 得到 200

#### Scenario: 数据库里没有密钥原文

- **WHEN** 登记项目后检查数据库文件的全部内容
- **THEN** 找不到密钥原文，只有摘要

#### Scenario: 密钥只在输出里出现一次

- **WHEN** `project add` 的标准输出含密钥；之后执行 `hubctl events`、`hubctl status --json`、`hubctl project list`，并检查服务日志文件
- **THEN** 这些输出和日志里都搜不到 `chub_`

#### Scenario: 反复猜密钥

- **WHEN** 同一个局域网来源地址（测试里注入，如 192.168.1.20）1 分钟内用错误的密钥请求 10 次，第 11 次用正确的密钥
- **THEN** 第 11 次是 429 `too_many_failures`，带 `Retry-After`；在被拒绝期间继续请求也不会延长；过了 1 分钟后正确的密钥恢复可用

#### Scenario: 本机的错误密钥挤不掉别的项目

- **WHEN** 来源是 127.0.0.1 的一个项目用错误的密钥请求 20 次，紧接着来源同样是 127.0.0.1 的另一个项目用正确的密钥请求 `GET /v1/status`
- **THEN** 前 20 次都是 401（没有一次 429），后一次是 200

#### Scenario: 换钥

- **WHEN** `rotate` 不带 `--grace`
- **THEN** 新密钥可用，旧密钥立刻 401；带 `--grace 10` 时旧密钥 10 分钟内仍可用，之后 401；`--grace 61` 被拒绝

#### Scenario: 宽限期内再换一次

- **WHEN** 密钥 K1 换成 K2（`--grace 10`），2 分钟后又换成 K3（不带 `--grace`）
- **THEN** K3 可用；K1 和 K2 都是 401

### Requirement: 修改、停用、启用、移除

- `hubctl project set <名字> [--prefix <前缀>] [--guaranteed <条>] [--cap <条>] [--label <标签> | --no-label] [--default] [--yes]`：改完同样要通过登记时的校验（前缀的规则、保底合计、上限、标签的规则），对下一个请求立即生效。改前缀、换掉已有的默认项目是需要确认的操作（`--yes`，规矩见 `hub-cli`）。已经收下的话不因为前缀改了而改变去向，已经用掉的条数不因为保底改小而退回。移除了的项目不能再改。
- `hubctl project disable <名字>`：立即生效。MUST 让这个项目此刻正挂着的取话请求也在返回前重新核对启用状态，以 403 `project_disabled` 结束、不交出任何话。正在发的那一条发完；它还没取走的话保留为"暂停"，重新启用后继续取（保留期照常计算，过了仍作废）；等确认的标记清掉；它没用完的保底从保护范围里放掉，别的项目马上能用。之后使用者发的、本来要交给它的话，由服务回"项目「x」已停用，这句话没处理"，不入队（见 `hub-inbox`）。
- `hubctl project enable <名字>`：重新校验保底总和，超了就拒绝并说明超了多少。
- `hubctl project remove <名字>`：必须先停用；是需要确认的操作。移除时它还没取走的话作废（清掉正文和对话凭证）；释放它的前缀；记录保留，名字不能再被新项目用。如果它是默认项目，并且还有别的能收话的项目（没移除、不是只推送），必须先用 `project set <另一个项目> --default` 换掉，提示里指明这条命令；没有别的能收话的项目时可以直接移除，之后不带前缀的话由服务回"没有设默认项目……"（见 `hub-inbox`）。

#### Scenario: 修改立即生效

- **WHEN** 项目的上限是 3、已经推送了 3 条，执行 `project set … --cap 5` 后紧接着再推送 1 条
- **THEN** 这 1 条放行，没有重启服务；再把保底改成大于上限、或者改成让保底合计超出窗口的数，都被拒绝，原设置不变

#### Scenario: 改前缀

- **WHEN** 项目 x 的前缀从 `x` 改成 `y`，队列里还有一条之前路由给它的话
- **THEN** 这条话仍然交给 x；之后"x 状态"不再交给 x（原样给默认项目），"y 状态"交给 x

#### Scenario: 停用后立刻断开

- **WHEN** 停用一个项目，它紧接着发消息和取话
- **THEN** 都是 403 `project_disabled`；它没用完的保底不再占着额度

#### Scenario: 停用时正在等的取话

- **WHEN** 项目有一个 `GET /v1/inbox?wait=30` 正挂着，此时执行 `project disable`，随后使用者发来一句本来要交给它的话
- **THEN** 挂着的请求以 403 `project_disabled` 结束，没有交出任何话；这句话由服务回"已停用"，不进队列

#### Scenario: 暂停的话重新启用后继续取

- **WHEN** 项目停用时队列里有两条没取走的话，3 分钟后重新启用；另一次是停用 11 分钟后才启用
- **THEN** 前一次启用后取话拿到这两条；后一次取话是空，两条记录都是"过期"

#### Scenario: 启用时保底超了

- **WHEN** 停用的项目保底 4，期间别的项目把保底提到 6（合计超出），再启用它
- **THEN** 拒绝启用并说明超了多少

#### Scenario: 移除

- **WHEN** 对一个启用中的项目执行 `remove`
- **THEN** 拒绝，提示先 `disable`；停用后 `remove` 成功，同名项目不能再登记，它的前缀可以被别的项目使用，它没取走的话的正文已清空

#### Scenario: 移除默认项目

- **WHEN** 默认项目 A 已停用，另有能收话的项目 B；执行 `remove A`；再 `project set B --default --yes` 后 `remove A`；另一种情形是 A 是唯一能收话的项目
- **THEN** 第一次拒绝并提示用 `project set B --default`；第二次成功；唯一项目的情形可以直接移除，之后没有默认项目

### Requirement: 项目之间互相看不到

每个请求 MUST 只能碰到自己项目的东西：取话只返回路由给自己的话；回复句柄只对被路由给自己的那句话有效，用别的项目的句柄或不存在的句柄一律 404 `unknown_handle`（两种情况返回一样）；去重键、发送记录、额度用量按项目分开，同一个去重键在两个项目里互不影响。`GET /v1/status` 只返回全局的登录和窗口信息，加上调用方自己的额度，不返回别的项目的名字和用量。

#### Scenario: 用别人的回复句柄

- **WHEN** 项目 B 拿着路由给项目 A 的那句话的回复句柄调用回复接口
- **THEN** 404 `unknown_handle`，没有向微信发任何东西

#### Scenario: 去重键各管各的

- **WHEN** 项目 A 和项目 B 各用同一个去重键 `daily` 发一条消息
- **THEN** 两条都发出去，互不影响

#### Scenario: 状态里没有别人

- **WHEN** 项目 B 调 `GET /v1/status`，项目 A 刚用掉了 5 条
- **THEN** 返回里有登录状态、窗口信息和 B 自己的额度；找不到 A 的名字、前缀或用量

### Requirement: 请求限速和大小

`POST /v1/messages` 与 `POST /v1/replies` 合计，每个项目每分钟最多 30 次（配置 `send.rate_per_minute`，滑动窗口）。认证通过的每个这样的请求都计数，不管后面成功还是被拒绝；超出的请求 MUST 返回 429 `rate_limited` 并带 `Retry-After`（距离最早一次计数满 1 分钟还要几秒，至少 1），不占额度、不留发送记录，也不再计数。任何请求体超过 64 KiB（固定值，按实际读到的字节算，不信请求头）返回 413 `too_large`。检查的先后：认证、限速、大小。

#### Scenario: 一个项目刷屏

- **WHEN** 一个项目在 1 分钟内连续发 31 次请求
- **THEN** 前 30 次按各自的规则处理，第 31 次得到 429 `rate_limited`；别的项目不受影响；最早一次请求满 1 分钟之后又可以发

#### Scenario: 被限速的请求不占额度

- **WHEN** 项目触发限速后又被拒绝了 3 次请求
- **THEN** 数据库里没有这 3 次的发送记录，窗口已用条数不变，恢复时间不因为这 3 次而推后

#### Scenario: 请求体太大

- **WHEN** 项目发一个 65 KiB 的请求体（包括不带 `Content-Length` 的分块请求）
- **THEN** 413 `too_large`，正文是统一的错误格式，不占额度、不留发送记录

### Requirement: 项目在线判断

一个项目满足下面任一条就算"在线"：此刻有一个它的取话请求正挂着；最近 `inbox.online_seconds`（默认 90）秒内它有过任何认证通过的 `GET /v1/inbox`（等到新话返回、等满超时返回、`max=0` 的心跳都算）或 `POST /v1/inbox/ack` 请求。已停用、已移除和只推送的项目永远不是"在线"。"在线"用于路由（见 `hub-inbox` 的项目没在线）和状态显示；它不影响发消息。每次认证成功的请求都 MUST 更新这个项目的"最后出现"时间。在线是读库、读内存现算的，不需要后台任务。

项目里处理一句话可能比 `inbox.online_seconds` 还久（现生成简报约 1 分钟，诊断一只股票几十秒），所以取话循环在处理期间要发心跳（`hub-client` 的 `run_inbox` 自带），自己写循环的项目要自己发。

#### Scenario: 取话停了

- **WHEN** 一个项目最后一次取话是 2 分钟前，此后只调过 `POST /v1/messages`
- **THEN** `hubctl project list` 里它显示离线，"最后出现"是它最近一次任何请求的时间

#### Scenario: 处理慢指令期间不算离线

- **WHEN** 项目取走一句话后处理了 120 秒，期间每 30 秒调一次 `GET /v1/inbox?wait=0&max=0`，第 120 秒时使用者给它发了另一句话
- **THEN** 项目一直是在线；使用者没有收到"没在线"的提醒，新话进了队列

#### Scenario: 挂着的请求算在线

- **WHEN** `inbox.max_wait` 配成 120，项目的 `GET /v1/inbox?wait=120` 已经挂了 100 秒（它到达的时间已经是 100 秒前，没有任何新请求）
- **THEN** 它是在线（此刻有请求挂着）；请求返回之后 90 秒内仍是在线，之后离线

#### Scenario: 只推送、停用的项目不在线

- **WHEN** 只推送的项目刚发完消息；另一个项目刚取过话就被停用
- **THEN** 两者在列表里都不是在线

### Requirement: 查看

`hubctl project list [--json]` 列出每个项目：名字、前缀、是不是默认、标签、保底、上限、是否启用、是否只推送、在线与否、最后出现、当前窗口已用条数；`_hub`、`_import` 不列。`hubctl project show <名字>` 看一个。输出里 MUST NOT 有密钥或摘要。已移除的项目默认不列，加 `--all` 才列（标明已移除）。

#### Scenario: 列表

- **WHEN** 登记了两个项目后执行 `hubctl project list`
- **THEN** 每个项目一行，包含以上各项；输出中搜不到 `chub_`

#### Scenario: 已移除的项目

- **WHEN** 移除一个项目后执行 `hubctl project list` 和 `hubctl project list --all`
- **THEN** 前者没有它，后者有并标明"已移除"

### Requirement: 配置与已有前缀冲突

`routing.confirm_words` 或 `hub.label` 被改成了和某个已登记项目的前缀相同的词，服务启动时 MUST 记一条警告事件，不拒绝启动；`hubctl doctor` 把它列为错误（见 `hub-cli`）。路由仍按固定的先后（服务自己的指令、前缀、确认话、默认项目）。

#### Scenario: 确认词撞上前缀

- **WHEN** 已有前缀为 `好` 的项目，配置把 `routing.confirm_words` 改成 `[对, 是, 确认, 好]` 后重启
- **THEN** 服务正常启动，事件里有一条警告；`hubctl doctor` 报错并指出是哪个前缀
