# Tasks

规矩：**每一项先写测试（看它失败），再写实现（看它通过）**；单元测试不联网；每个阶段做完跑 `uv run ruff format --check && uv run ruff check && uv run pytest -q`，全绿才算这个阶段完成，并单独向使用者汇报、验收。**阶段 A 到 C 的验收一律是 pytest 驱动的**（不依赖后面阶段才写的命令），`curl` 之类的手工演示放到阶段 D。使用者点头规格和测试清单之前，下面一项都不开始。

以 `[云]` 标的在云里的线程做，以 `[Mac]` 标的要在家里的 Mac mini 上做（由使用者授权，经协调者转给 Mac 上的线程）。

  - **规格没写、这里定下的小约定**（`api.py` 的模块注释里也有）：①取话：只推送的项目先于参数校验回 403 `push_only`；`wait`、`max` 只认 ASCII 数字（`+1`、`1.5`、空串、全角数字、带空白都是 400），`max=0` 时 `wait` 照样校验，同一个参数写了几次取最后一个，不认识的参数忽略；很长的数字串只取前 13 位再截到上限，不会因为转整数出错；②确认：只推送的项目不拦（它没有待取的话，全部算 `unknown`）；`ids` 一次最多 50 个，重复的也各占一个名额；元素不是字符串、没法编码成 UTF-8 的 400；③回复：`confirm_seconds` 不管有没有 `awaiting_confirmation` 都要合格，`null`、`1.5`、`true` 都不是正整数，`awaiting_confirmation` 必须是真正的布尔值；回复次数在发送成功以后才记，所以同一个句柄同时到的几个回复可能一起通过次数检查（最多多出同时在途的那几个）；`reply_limit` 的 `Retry-After` 是句柄还有几秒失效（向上取整，至少 1）；认证之后到发出之间项目被停用的，回复照发（只有推送发出前再核对一次）；④项目的取话请求在客户端中途断开时服务并不知道：最坏挂到 `inbox.max_wait`（55 秒），它的下一个取话请求会把它顶掉；租出去却没人收的话，租期过了照常再给一次，`attempt` 加 1。
  - 故意改坏的检查：`api.py` 里这三个接口 119 处，`inbox.py` 新加的关闭和回复次数用完的等待秒数 27 处，`services.py` 的接线 6 处，共 152 处，全部抓到。
