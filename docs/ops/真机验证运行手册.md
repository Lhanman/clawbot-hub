# 真机验证运行手册

E4 在真账号上走一遍的顺序和命令。《真机验证清单》说每一项量什么、结果填到哪里；这份说一次完整的验证**怎么走**：谁在场、先后顺序、每一步的命令和预期、出事怎么退。

**使用者在场并明确授权后才做。** 授权的范围就是清单里的那些项；没有写在这里的腾讯请求一律不做。

## 先记住的几条

- **不再扫码。** `hubctl login`、`hubctl import-credentials --replace` 一律不碰：一个微信号可能只认最后一次扫码，再扫会挤掉正在用的绑定。
- **碰到 `-14`（登录失效）立刻停**：先按第 6 段恢复旧的微信问答，再告诉使用者。要不要重新扫码由使用者定；重新扫码以后备份的旧凭证就作废了。
- **同一时间只能有一个程序向腾讯收消息**：旧的微信问答、E4 的服务、探针，三者只能有一个在收。
- 登录凭证、对话凭证、消息正文不进日志、报告、提交和聊天。探针只记形状（状态码、返回体的键名和类型、耗时、条数），结果追加在 `<E4 数据目录>/e4-results.jsonl`。
- 每条 `hubctl` 命令都带 `--home ~/.clawbot-hub-e4`：不带的话，连 `hubctl version` 也会在 `~/.clawbot-hub` 建出一个空目录。
- 额度：第 3、4、5 段一共约 16 条（第 3 段 8 条、第 4 段 2 到 4 条、第 5 段 6 条），分在四个窗口里，每个窗口都不超过 10 条。探针自己有总数上限：一共最多发 20 条，记在数据目录的 `e4-sends.count`，分几次跑也合计（用 `HUB_LIVE_MAX_SENDS` 改）；服务发的那几条不在内。占满一个窗口的清单第 5 项（窗口时长和条数）这次**不做**，要做另问使用者。
- 使用者要发话四次：第 3 段一次、第 4 段两次、第 5 段一次，最后恢复旧问答时再一次。内容随意（比如「测试」），**不要发「简报」「状态」这类旧问答认得的指令**，也不要以「服务」开头（那是 hub 的指令词）。
- 探针或服务打印以 `▶ 请用户` 开头的行时，马上转告使用者；使用者喊停，直接跳到第 6 段。
- 这台 Mac 访问腾讯走系统代理时，出现 `ProxyError` 要和腾讯自己的行为分开记（结果里的 `via_proxy` 会写）。

## 第 0 段：准备（不连腾讯，不占额度，不动微信问答）

```
cd ~/clawbot-hub
git fetch origin && git checkout -B main origin/main && uv sync
lsof -nP -iTCP:18793 -sTCP:LISTEN
ls -ld ~/.clawbot-hub-e4 2>&1
```

预期：`git` 之后 `HEAD` 是最新的 `main`；`lsof` 没有输出（18793 空闲；18789、18792 被别的程序占着，不要用）；`ls` 说目录不存在。

只读地看一眼旧微信问答的现状，记下基线（不要贴令牌）：

```
launchctl list | grep ashare
cd <ashare-quant 目录> && uv run aq wechat status
```

预期：旧问答（`aq wechat serve`）在跑；`status` 在它跑着的时候只读状态文件，打印绑定时间、对话窗口还剩多久（早就过期了也正常，要使用者发话才会重开）。

## 第 1 段：停旧问答，把凭证导进 E4 的数据目录　**使用者在场**

先停旧问答，确认真的停了：

```
launchctl bootout gui/$(id -u)/com.ashare-quant.wechat
launchctl list | grep com.ashare-quant.wechat || echo 没有在运行
```

预期：打印「没有在运行」。从这里到第 6 段恢复为止，使用者发给 ClawBot 的话旧问答不会回。（不要用 `pgrep -f` 找进程：它会把运行这条命令的 shell 自己也找出来。）

复制凭证、建 E4 的数据目录和配置、导入、**立刻删掉复制件**：

```
cp -p "<ashare-quant 目录>/data/notify/clawbot.json" ~/clawbot-e4-creds.json
chmod 600 ~/clawbot-e4-creds.json
mkdir -p ~/.clawbot-hub-e4 && chmod 700 ~/.clawbot-hub-e4
cat > ~/.clawbot-hub-e4/config.yaml <<'EOF'
server:
  port: 18793
EOF
chmod 600 ~/.clawbot-hub-e4/config.yaml
cd ~/clawbot-hub
uv run hubctl import-credentials ~/clawbot-e4-creds.json --probe --home ~/.clawbot-hub-e4
rm ~/clawbot-e4-creds.json
```

预期：只有摘要，没有任何凭证——机器人末 4 位、使用者（打码）、绑定时间、对话窗口（过期了就写「已经过期」）、最后一句「探针：凭证有效（腾讯没有拒绝）」。**写着「凭证已经失效（腾讯回 -14）」就停**，按第 6 段恢复，告诉使用者，不要扫码。写着「没能确认」多半是代理（`ProxyError`）或网络，记下原因，别重试超过两次。

## 第 2 段：不占额度的探针

下面所有 `pytest` 命令之前先在这个终端里设好：

```
cd ~/clawbot-hub
export HUB_LIVE_HOME=~/.clawbot-hub-e4 HUB_TEST_TIMEOUT=0
```

取码、查一次状态（不扫）和 `notifystart` 的两个路径：

```
uv run pytest -m live -n0 -s tests/live/test_real_ilink.py -k "official_qrcode_post or qr_login_from_home_network or notify_paths"
```

预期：3 个通过（`qr_login_from_home_network` 的状态多半是 `wait`）；每一步打印一行 `[项] 步: 键=值`，结果同时追加进 `e4-results.jsonl`。通过不代表腾讯同意了：`official` 取码、`notifystart` 哪个路径可用，看打印和记录里的状态码、键名。

长轮询空闲时腾讯怎么回（**这几分钟请使用者不要给 ClawBot 发消息**，探针打印「▶ 请用户先不要……」时转告）：

```
uv run pytest -m live -n0 -s tests/live/test_real_ilink.py -k long_poll_timeout_round_trip
```

预期：量两次空闲，每次最多 90 秒；记录里 `kind` 是 `empty_response`（腾讯自己回了个空结果，看 `elapsed_seconds`）或 `client_read_timeout`（挂到我们读超时）。

## 第 3 段：要使用者发话的探针（占约 8 条额度）

三项连着跑，前一项收到的那条消息的对话凭证给后两项用（90 秒内有效，过了探针会再请使用者发一句）：

```
uv run pytest -m live -n0 -s \
  tests/live/test_real_ilink.py::test_old_buf_redelivers \
  tests/live/test_real_ilink.py::test_message_id_in_send_response \
  tests/live/test_real_ilink.py::test_legacy_vs_official_profiles
```

探针打印「▶ 请用户现在在微信里给 ClawBot 发一句话」时转告使用者，内容随意（比如「测试」），**不要发「简报」「状态」这类旧问答认得的指令**（旧问答恢复后可能把这条当新消息回一遍）。探针收到以后往下走，不用再催。

预期：3 个通过；记录里有 `first_batch`、`old_buf_again`（`same_seqs_as_first` 就是重发不重发）、`new_buf_again`、`normal_1`…`normal_3`、`no_context_token`、`legacy_1/2`、`official_1/2`。跑完请使用者告诉你：微信里收到了几条「E4 验证」（最多 4 条，对比那条多半收不到）、几条「E4 对比」（应有 4 条），记进结果。

## 第 4 段：服务层面的检查（占 2 到 4 条额度，顺带测 Bark）　**使用者在场，要发两次话**

和演练一样装一个单独的 launchd 任务（label `com.clawbot-hub.e4`，数据目录 `~/.clawbot-hub-e4`，端口已经在配置里写了 18793），做法见《安装说明》第 8 步括号里的说明；**这时候探针都已经跑完，没有 `pytest` 在跑**。

```
cd ~/clawbot-hub
sed -e "s|__LABEL__|com.clawbot-hub.e4|g" \
    -e "s|__REPO_DIR__|$HOME/clawbot-hub|g" \
    -e "s|__UV_PATH__|$(command -v uv)|g" \
    -e "s|__DATA_DIR__|$HOME/.clawbot-hub-e4|g" \
    deploy/launchd/com.clawbot-hub.serve.plist.example \
    > ~/Library/LaunchAgents/com.clawbot-hub.e4.plist
plutil -lint ~/Library/LaunchAgents/com.clawbot-hub.e4.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.clawbot-hub.e4.plist
sleep 5
uv run hubctl status --home ~/.clawbot-hub-e4
uv run hubctl doctor --online --home ~/.clawbot-hub-e4
```

预期：服务在运行，登录一栏已绑定；`doctor` 没有 ✗。第 3 段的探针只推进了收消息的进度，没有替服务开窗口，所以「对话窗口」此刻多半写着已经过期或没有，正常：窗口要等服务自己收到使用者的话才会开。

先登记测试项目——**先登记，再请使用者发话**，不然服务会回一句「没有默认项目」：

```
uv run hubctl project add e4 --prefix 测试 --guaranteed 2 --cap 6 --default --home ~/.clawbot-hub-e4
export CLAWBOT_HUB_KEY=<上一条命令只显示一次的密钥>
```

**第一次（`legacy` 档，默认）**：请使用者在微信里给 ClawBot 发一句话。发出以后马上看窗口、马上发（对话凭证可能只管一两分钟，别拖）：

```
uv run hubctl status --home ~/.clawbot-hub-e4
uv run hubctl send --url http://127.0.0.1:18793 "E4：服务发的第一条（测试消息，可忽略）"
sqlite3 ~/.clawbot-hub-e4/hub.db "select kind, status, no_message_id from outbox order by created_ms desc limit 3"
```

预期：`status` 里「对话窗口」是刚开的；`hubctl send` 输出 `sent`，退出码 0（窗口没开、凭证过期或额度用完会是 `rejected`，退出码 5，把原因原样记下）；`sqlite3` 最上面一行 `push|sent|0`（腾讯给了消息编号）或 `push|sent|1`（没给）。使用者在微信里会多收到一条服务自己回的话（测试项目没有人在取，服务回「不在线」一类的提示，占 1 条额度）——这是服务在按设计回复，也是一次服务回话成功与否的实测，把它收到没收到记下。

**第二次（`official` 档）**：改配置、重启，看启动时 `notifystart` 有没有报错：

```
cat > ~/.clawbot-hub-e4/config.yaml <<'EOF'
upstream:
  profile: official
server:
  port: 18793
EOF
chmod 600 ~/.clawbot-hub-e4/config.yaml
launchctl bootout gui/$(id -u)/com.clawbot-hub.e4
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.clawbot-hub.e4.plist
sleep 5
uv run hubctl events --kind lifecycle --limit 10 --home ~/.clawbot-hub-e4
```

预期：`events` 里没有 `notifystart` 的警告（有就把原文记下，不影响使用）。然后请使用者**再发一句话**（上一个窗口里的对话凭证不拿来用，换新的，这样两档的对比不被凭证新旧搅乱），马上发：

```
uv run hubctl send --url http://127.0.0.1:18793 "E4：official 档发的一条（测试消息，可忽略）"
sqlite3 ~/.clawbot-hub-e4/hub.db "select kind, status, no_message_id from outbox order by created_ms desc limit 3"
```

预期：同样 `sent`；`no_message_id` 和 `legacy` 档比一比。服务回的「不在线」提示在 `inbox.offline_notice_seconds` 秒内同一个项目只回一次，所以这次多半没有。

Bark（使用者愿意测才做）：设备码是秘密，**请使用者自己在 Mac 的终端里输入**，不要贴进聊天：

```
uv run hubctl alerts set-key --home ~/.clawbot-hub-e4
uv run hubctl alerts test --home ~/.clawbot-hub-e4
```

预期：`alerts test` 报告 Bark 收到了，使用者手机上响一声。

做完这一段，**停掉 E4 的服务**再往下：

```
launchctl bootout gui/$(id -u)/com.clawbot-hub.e4
uv run hubctl status --home ~/.clawbot-hub-e4 | head -1
```

预期：第一行是「服务：没有在运行」。

## 第 5 段：对话凭证能用多久（占 6 条额度，要 35 分钟左右）

服务停着，只有这一个探针在收：

```
uv run pytest -m live -n0 -s tests/live/test_real_ilink.py::test_context_token_lifetime
```

探针请使用者发一句话（「▶ 请用户……」），收到以后按 0、1、2、5、10、30 分钟各用这条消息的对话凭证回复一条，第一次被拒绝就停。期间每 5 分钟打印一行等待的进度。跑完请使用者告诉你收到了哪几条「E4 回复」，记进结果（腾讯可能回「成功」却不投递）。

## 第 6 段：收尾，恢复旧的微信问答

不管前面走到哪一段、是做完了还是半路喊停，都从这里收尾：

```
launchctl bootout gui/$(id -u)/com.clawbot-hub.e4 2>/dev/null
rm -f ~/Library/LaunchAgents/com.clawbot-hub.e4.plist
launchctl list | grep clawbot-hub || echo 没有 E4 的任务
lsof -nP -iTCP:18793 -sTCP:LISTEN || echo 18793 空闲
python3 - <<'EOF'
import json, os
home = os.path.expanduser("~/.clawbot-hub-e4")
token = json.load(open(home + "/account.json"))["bot_token"]
text = open(home + "/e4-results.jsonl", encoding="utf-8").read()
print("结果里出现了登录凭证，不要拷出去！" if token in text else "结果里没有登录凭证")
EOF
cp ~/.clawbot-hub-e4/e4-results.jsonl ~/e4-results-$(date +%Y%m%d).jsonl
rm -rf ~/.clawbot-hub-e4
ls ~/.clawbot-hub-e4 2>&1
```

预期：没有 E4 的任务、18793 空闲；「结果里没有登录凭证」（复制出来的 `e4-results.jsonl` 里只有形状，没有凭证和正文）；`ls` 说目录不存在（E4 的数据目录里有一份登录凭证，必须删，不是移走）。（不要用 `pgrep -f` 找进程：它会把运行这条命令的 shell 自己也找出来。）

让旧问答把 E4 期间攒下的消息咽掉，再起来。`aq wechat status` 在旧问答没跑的时候会向腾讯收一次新消息并存下最新的进度，所以旧问答恢复后不会把 E4 期间使用者发的测试消息当新指令回一遍：

```
cd <ashare-quant 目录> && uv run aq wechat status
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.ashare-quant.wechat.plist
sleep 3
launchctl list | grep com.ashare-quant.wechat
```

预期：`status` 打印绑定状态和最新的对话窗口；`launchctl list` 那一行第一列是一个进程号（不是 `-`）。**最后请使用者给 ClawBot 发一句「状态」，几秒内应该收到旧问答的回复**，才算恢复；这一句同时重开了对话窗口。

## 回报什么

交给云里的线程回填文档和默认值：

1. `e4-results.jsonl`（只有形状）和使用者在微信里看到的情况（收到几条）；
2. 每个探针是否通过、有没有出现 `ProxyError`、`-14`、被拒绝的代码（数字）和原文（打码）；
3. 第 4 段服务层面的现象：两次 `hubctl send` 的结果和 `no_message_id`、服务自己回的「不在线」提示使用者收没收到、`notifystart` 有没有警告、`doctor --online` 的结果、Bark 收没收到；
4. 旧问答是否恢复（`launchctl list` 的进程号和使用者的「状态」回复）；
5. 任何和预期不一样的地方，原样写，不要自己去改文档或默认值。

量到的值回填到《真机验证清单》末尾的「结果记录」、配置默认值（`upstream.confirm`、`upstream.profile`、`reply.handle_minutes` 等）和规格，由云里的线程做，改默认值之前要使用者点头。
