# ClawBot 协议与规则调研

日期：2026-10-09 起，2026-10-10 补充。目的：把"腾讯到底规定了什么、我们只是听说了什么、还有什么没弄清"分开写，作为服务设计的依据，也是真机验证（`docs/ops/真机验证清单.md`）的出发点。

标记约定：**官方**（腾讯自己的文档或代码）、**用户报告**（腾讯仓库问题单里别人的描述，没有腾讯人员回复）、**第三方**（社区文档、开源项目）、**本项目实测**、**推断**。

## 1. 协议（官方）

来源：[openclaw-weixin 协议文档](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)（基于插件 2.4.8 的客户端代码；文档自己说"客户端类型和行为不等于完整的服务端约定"）。

- 传输：HTTPS + JSON，默认地址 `https://ilinkai.weixin.qq.com`。
- 请求头：`Content-Type: application/json`、`AuthorizationType: ilink_bot_token`、`Authorization: Bearer <bot_token>`、`X-WECHAT-UIN`（随机 uint32 的十进制字符串再 base64）、`iLink-App-Id: bot`、`iLink-App-ClientVersion`（版本号按 `0x00MMNNPP` 编成十进制字符串，2.4.8 是 `132104`）、可选 `SKRouteTag`。
- 请求体里的 `base_info`：`channel_version`（插件版本，例子是 `2.4.8`）、`bot_agent`（可选的观测标识）。
- 返回里的 `ret`、`errcode`、`errmsg` 不是每个接口都有；`ret: 0` 表示成功。
  - `getUpdates`：任一为 -14 触发"把该账号暂停 1 小时"；其他失败走重试退避。
  - `sendMessage`：非 0 的 `ret` 抛错；**没有 `ret` 不触发检查**。文档给的成功返回示例是 `{"ret":0,"errmsg":""}`，**没有消息编号**。
  - `notifyStart` / `notifyStop`：失败只记警告，不挡启动和退出。
- 扫码登录：`POST /ilink/bot/get_bot_qrcode?bot_type=3`，请求体 `{"local_token_list": []}`（客户端最多带本地存的最近 10 个登录凭证）；`GET /ilink/bot/get_qrcode_status?qrcode=…`（要验证码时加 `verify_code`）。状态：`wait`、`scaned`、`confirmed`（带 `bot_token`、`ilink_bot_id`、`baseurl`、`ilink_user_id`）、`expired`、`need_verifycode`、`verify_code_blocked`、`scaned_but_redirect`（改用 `redirect_host`）、`binded_redirect`（"这个 bot 已经绑定在当前实例上"）。
- 收消息：`POST /ilink/bot/getupdates`，请求带上次返回的 `get_updates_buf`（第一次是空串），服务端挂住请求直到有消息或到长轮询超时；返回 `msgs`、新的 `get_updates_buf`、可选的 `longpolling_timeout_ms`（服务端建议的超时，例子是 35000）。
- 发消息：`POST /ilink/bot/sendmessage`，`msg` 里 `from_user_id` 为空、`to_user_id`、`client_id`（客户端生成）、`message_type: 2`（机器人）、`message_state: 2`（一次发完）、`context_token`（回复哪条对话就带哪条收到的凭证）、`item_list`（文字项 `type: 1`）。缺 `context_token` 时官方客户端只记警告、照发，服务端接不接受没说。
- 消息模型：`seq`、`message_id`（数字）、`from_user_id`、`to_user_id`、`client_id`、`create_time_ms`、`message_type`（1 用户、2 机器人）、`message_state`、`item_list`、`context_token`。条目类型 1 文字、2 图片、3 语音、4 文件、5 视频；条目可带 `ref_msg`（引用的消息）。
- 官方文档没写：窗口时长、条数上限、一个微信号能绑几个登录、`context_token` 的有效期、发送返回里有没有消息编号。

### ashare-quant 现在的实现（`legacy`）和官方插件的差别

| | ashare-quant 现在 | 官方插件（`official` 档位补齐） |
|---|---|---|
| 请求头 | `Content-Type`、`AuthorizationType`、`Authorization`、`X-WECHAT-UIN` | 另有 `iLink-App-Id`、`iLink-App-ClientVersion` |
| `base_info` | 只有 `channel_version: "1.0.2"` | `channel_version: "2.4.8"` 加 `bot_agent` |
| 启动 / 停止 | 不调用 | `notifystart` / `notifystop` |
| 取二维码 | `GET` + 参数（在真实账号上能用） | `POST` + `{"local_token_list": []}`（官方文档的写法，没在真账号上试过，能不能用待真机验证） |
| 长轮询超时 | 固定 45 秒 | 用服务端建议的 `longpolling_timeout_ms` |
| 发送成功的判定 | HTTP 200 且没有错误码 | 非 0 的 `ret` 才算失败 |
| `-14` | 每 10 分钟探测一次 | 暂停该账号 1 小时 |

ashare-quant 的实现已经在真实账号上跑了几周；服务端有没有开始校验多出来的请求头，不知道。所以服务默认 `legacy`，`official` 做成配置，真机验证后再决定。

## 2. 规则（非官方，会变）

| 事 | 说法 | 性质 |
|---|---|---|
| 使用者发一条消息后，24 小时内机器人最多能发 10 条 | 来自用户在腾讯仓库提的需求单 [#202](https://github.com/Tencent/openclaw-weixin/issues/202)（腾讯只回了"在重新评估"）和第三方文章 | 用户报告 / 第三方 |
| 实测对不上 | [#309](https://github.com/Tencent/openclaw-weixin/issues/309)：约 11–16 小时没有使用者的消息后，主动推送就开始被拒 | 用户报告 |
| 回复用的对话凭证有效期 | [#286](https://github.com/Tencent/openclaw-weixin/issues/286)：有人测到只有 1–2 分钟 | 用户报告 |
| "成功"但没送到 | [#330](https://github.com/Tencent/openclaw-weixin/issues/330)、[#337](https://github.com/Tencent/openclaw-weixin/issues/337)（10 月 9 日当天还有新的）：发送返回成功、没有消息编号、微信里看不到；[#287](https://github.com/Tencent/openclaw-weixin/issues/287)：正常账号的返回里有数字的 `message_id`，送不到的账号只有 `{"ret":0}` | 用户报告 |
| 一个微信号只认一个登录 | 第三方 WeiLink 文档："同一时间只能绑一个 bot，登录新 bot 会自动解绑旧的"；[#295](https://github.com/Tencent/openclaw-weixin/issues/295)（提问人后来改口）、[#330](https://github.com/Tencent/openclaw-weixin/issues/330)（换绑后恢复）、[#252](https://github.com/Tencent/openclaw-weixin/issues/252)（凭据丢了之后新二维码立刻过期）、[#260](https://github.com/Tencent/openclaw-weixin/issues/260)（问多个微信扫码，没人回）；本项目 2026-10-10 00:32（东京时间）的掉线时间线与之吻合 | 第三方 / 用户报告 / 本项目实测，原因是推断 |
| `-14` 出现在长时间闲置之后 | [#155](https://github.com/Tencent/openclaw-weixin/issues/155) | 用户报告 |
| 云服务器上扫码被拦 | [#333](https://github.com/Tencent/openclaw-weixin/issues/333)（10 月 2 日）：新加坡云服务器上确认时微信提示"运行环境存在风险，暂无法连接"，官方插件的登录函数同样被拦；家用宽带没有测试结果 | 用户报告 |

## 3. 第三方资料

- [OpeniLink Hub](https://github.com/openilink/openilink-hub)（MIT 许可，约 1.6k 星，10 月 9 日读了 README）：开源的 ClawBot 中转。应用通过 WebSocket 或 Webhook 接入，用"/命令"或"@应用"触发；支持多个微信号和窗口到期提醒。**没有提到**条数额度、送达确认、重试。第三方代码持有登录凭证、能看到所有消息；项目自称"仅供学习交流"、和腾讯无关。
- Rust 写的 [ilink-hub](https://docs.rs/crate/ilink-hub/0.2.8)：对外假装成腾讯的接口，现有客户端理论上只改地址就能接；收消息有独占锁。页面当时打不开，来自搜索摘要，待核实。
- [WeiLink 文档](https://weilink.readthedocs.io/en/latest/usage/concepts/)：同上，来自搜索摘要，待核实。

## 4. 还没弄清的事和怎么弄清

| # | 问题 | 为什么重要 | 怎么弄清（真机验证清单里） |
|---|---|---|---|
| 1 | 发送成功的返回里有没有消息编号 | 决定"送达确认"能不能用严格档 | 在真账号上发几条，记录返回体里的字段（不记正文），再试一次窗口外的发送对比 |
| 2 | 一个微信号是不是只认最后一次扫码的登录 | 决定"只有服务能扫码"这条规矩是不是必须 | **不要用再扫一次来试**（会挤掉正在用的绑定）；问使用者 10 月 10 日 00:16–00:32（东京时间）有没有给别的项目扫过码；以后有第二个项目接入时观察 |
| 3 | 窗口真实长度和条数 | 决定默认值 | 在不影响日常使用的时段，用服务的发送记录和被拒绝的时间点估算 |
| 4 | 回复用的对话凭证能用多久 | 决定回复句柄的有效期 | 取一条消息后每隔一段时间回复一次，记录第一次被拒绝的时间 |
| 5 | `legacy` 与 `official` 在真账号上有没有差别 | 决定默认档位 | 两档各发一批，对比结果（先用 `legacy` 作基线） |
| 6 | 家用网络能不能正常扫码 | 服务要放在 Mac mini 上 | 迁移时用导入凭证绕开；万一要重新扫码，在家里网络试 |
| 7 | 新扫码以后旧凭证是不是立刻失效 | 决定切换时能不能"先扫新的再停旧的" | 切换步骤按"先停旧再启新、用导入不重新扫码"写，不依赖这个答案 |

## 5. 对设计的影响

| 事实 / 不确定 | 设计怎么应对 |
|---|---|
| 一号一绑不确定 | 按"成立"设计：只有服务登录、收消息，进程锁保证单实例；迁移用导入凭证，不重新扫码 |
| 窗口、条数、凭证有效期不是官方的、在变 | 全是配置；腾讯拒绝后暂停并告警；窗口快到期提醒使用者 |
| 假成功、没有编号 | "送达确认"是一个三档开关，默认观察、真机验证后再严格；未确认的不偷偷重发 |
| 官方文档示例里发送返回没有编号 | 不把"没编号"直接当失败，免得正常账号每次都被判未确认 |
| 读超时不知道到没到 | 不重试，标"未确认"，交给调用方（Bark 兜底） |
| 云上扫码被拦 | 服务和扫码都放在家里的 Mac mini |
| 协议版本与官方插件有差距 | 上游适配层 + `legacy` / `official` 两档，协议变化只改一处 |
| 官方在 `-14` 后暂停 1 小时 | 探测间隔做成配置（默认 600 秒，与现在一致），不在代码里写死 |
| 消息里有 `ref_msg`（引用） | 以后可以做"回复（引用）某条消息时跟着那条消息的项目走"，第一版不做 |
