# 真机验证清单

腾讯一侧的规则，只能在真账号上量。单元测试和合约测试用的是假腾讯（`tests/support/fake_ilink.py`），它的行为是照协议文档和用户报告**猜**的；下面这些猜测，必须在真机上确认，确认以后把实测值回填到文档和配置默认值里。

这份清单和 `tests/live/test_real_ilink.py` 里的 11 个测试骨架**一一对应**（每项标题里的名字就是测试函数名，多一个少一个都会让文档测试报错）。真机测试默认不跑，用 `uv run pytest -m live` 才跑。

## 动手之前

1. **要使用者在场并明确授权。** 这些测试会访问真实的腾讯接口，不装联网守卫，不清代理环境。开始之前先和使用者讲清楚：每一项会占用多少条**额度**（下面每项都写了），会不会影响现有的微信问答。
2. **不要再扫码来试。** 一个微信号可能只认最后一次扫码，再扫一次会把正在用的绑定挤掉（`test_one_login_per_wechat` 就是为了弄清这件事，所以只观察，**不要再扫**一次来试）。取二维码的测试只取码、不扫。
3. **不影响日常使用的时段做**，并且先确认服务和 ashare-quant 的微信问答没有同时在收消息（同一时间只能有一个程序向腾讯收消息）。
4. 量到的值**不写进测试文件**：写在本文末尾的「结果记录」表里，再回填到配置默认值（`src/clawbot_hub/config.py`）、设计文档和规格里。
5. **用探针跑，不手敲请求。** `tests/live/probes.py` 里每一项一个函数，只做下面写的请求，只记形状（状态码、返回体的键名和类型、耗时、条数；登录凭证、对话凭证、消息正文不进输出和结果文件），结果追加在 E4 数据目录的 `e4-results.jsonl`；`tests/live/test_real_ilink.py` 里的真机测试调它们，设了 `HUB_LIVE_HOME`（E4 的数据目录）才跑，没设就跳过。探针本身对着假腾讯自测过（`tests/live/test_probes_selftest.py`，每次都跑）。先后顺序、每一步的命令、谁在场、出事怎么退，见《真机验证运行手册》；这份清单只说每一项量什么、结果填到哪里。

额度账：窗口是使用者发话后开的，默认 24 小时 10 条（用户报告，不是官方的）。下面会用掉额度的项合计最多约 20 条，要分成不同的窗口做，或者每项做之前先在微信里给 ClawBot 发一句话重新开窗口。

建议顺序（先做不占额度、风险低的）：`test_launchd_umask_for_log` → `test_qr_login_from_home_network`（只在家里网络上取码确认）→ `test_official_qrcode_post` → `test_notify_paths` → `test_long_poll_timeout_round_trip` → `test_old_buf_redelivers` → `test_message_id_in_send_response` → `test_legacy_vs_official_profiles` → `test_window_length_and_quota` → `test_context_token_lifetime`，`test_one_login_per_wechat` 是观察项，随时记。

## 1. `test_message_id_in_send_response`：发送返回里到底有没有消息编号

**决定什么：** `upstream.confirm` 能不能从默认的 `observe` 改成 `strict`。`strict` 档才会把「腾讯回了成功但没有消息编号」判成 `unconfirmed`；官方文档的示例返回是 `{"ret":0,"errmsg":""}`，没有编号，「有编号才算送达」只来自用户在腾讯问题单里的报告。

**占额度：** 约 4 条（3 条正常 + 1 条对比）。

**怎么测：** 已绑定、窗口开着（先在微信里给 ClawBot 发一句话）。用 `legacy` 档发 3 条短消息，记录每次返回体里出现的**键名**（不记正文）。再在窗口外（或使用者没发过话的状态下）试一次作对比。服务在 `observe` 档下每条发送都会记「腾讯有没有给消息编号」：`sqlite3 ~/.clawbot-hub/hub.db "select status, no_message_id from outbox order by created_ms desc limit 4"`（发送记录里没有正文）。探针里对比的那一条是不带对话凭证发的；服务层面的 `no_message_id` 在运行手册第 4 段看。

**怎么记：** 记下返回体里的键名（`message_id`？`msg_id`？别的名字？是数字还是字符串）；3 条正常的是不是每条都有；对比那一条有没有。填进结果记录表。

**回填：** 正常账号的返回里有编号 → 把 `upstream.confirm` 的建议值改成 `strict`，请使用者点头后再改默认值；编号的键名不在 `send.message_id_keys`（默认 `message_id`、`msg_id`）里的话补进去；没有编号 → 保持 `observe`，并把「有编号才算送达」的说法从文档里删掉。

**已量到：** 2026-10-18（东京时间）在 Mac mini 上的真账号里量到。8 次发送全部回 HTTP 200，返回体只有一个键 `message_id`（整数），3 条正常的每条都有。**对比那条（不带对话凭证）也回了整数 `message_id`，手机却没有收到。** 所以：正常账号的返回里有编号，`send.message_id_keys` 的默认值不用改；但编号只说明腾讯收下了，**不能当作送到了**——「有编号才算送达」这句话要改成「有编号只说明腾讯收下了」。`strict` 能挡的只是用户报告里「腾讯回成功却没有编号」那一类，挡不了不带凭证这一类。按本项的回填规则，`upstream.confirm` 可以建议改成 `strict`，默认值仍是 `observe`，要使用者点头才改；云里线程的建议是先让服务用 `observe` 跑一周，`hubctl status` 里的「没有编号」一直是 0 再改（一个配置项，随时可改）。

## 2. `test_legacy_vs_official_profiles`：`legacy` 与 `official` 两档有没有差别

**决定什么：** `upstream.profile` 要不要切到 `official`（多带 `iLink-App-Id`、`iLink-App-ClientVersion`、`channel_version 2.4.8`、`bot_agent`，并调 `notifystart` / `notifystop`）。默认 `legacy`，和 ashare-quant 现在发的请求一致，已知能用。

**占额度：** 约 4 条（每档 2 条）。

**怎么测：** 先用 `legacy` 作基线发 2 条，再把 `config.yaml` 里 `upstream.profile` 改成 `official`、重启服务（`launchctl bootout`，隔 3 秒再 `bootstrap`），发 2 条。对比：是否都成功、返回体是否一样、有没有被拒绝。做完改回 `legacy`。探针不起服务，直接用两档的请求头各发 2 条；改 `config.yaml`、重启、看 `notifystart` 的那一次在运行手册第 4 段。

**怎么记：** 两档各自的结果（`sent` / `unconfirmed` / `rejected`）、返回体键名有没有差别、`official` 下启动时的 `notifystart` 有没有报错（看 `hubctl events --kind lifecycle`）。

**回填：** 结果一致 → 默认仍是 `legacy`，把「official 已在真账号上验证」写进文档；有差别 → 写下差别，决定默认值。

## 3. `test_official_qrcode_post`：官方档的 POST 取二维码

**决定什么：** `official` 档下取二维码改用 `POST /ilink/bot/get_bot_qrcode?bot_type=3`、请求体 `{"local_token_list": []}`，官方文档里这样写，**没有在真账号上试过**；`local_token_list` 固定发空数组对服务端有没有影响也不知道。

**占额度：** 0 条（只取码）。

**怎么测：** 对着真实接口发这个 `POST`，只取码，**不要扫这张码**（扫了会挤掉正在用的绑定）。看返回有没有 `qrcode` 和 `qrcode_img_content`。

**怎么记：** 返回的形状和 `legacy` 的 `GET` 一样不一样；HTTP 状态；有没有报错信息（原文记下，打码）。

**回填：** 形状一样 → `official` 档的取码流程可用；不一样 → 改 `upstream/http.py` 和假腾讯。

## 4. `test_notify_paths`：`notifystart` 的路径

**决定什么：** `official` 档下服务启动时调 `notifystart`、正常退出时调 `notifystop`。官方文档里有两个路径写法：`/ilink/bot/notifystart` 和 `/ilink/bot/msg/notifystart`，哪个可用不确定。

**占额度：** 0 条。

**怎么测：** `official` 档下分别请求这两个路径，记录 HTTP 状态码和返回体。只测 `notifystart`，**不调 `notifystop`**（不知道它会不会让腾讯停止投递）。

**怎么记：** 两个路径各自的状态码、返回体摘要（`ret` 值）。

**回填：** 可用的那个写进 `upstream/http.py` 和假腾讯；两个都不可用 → 记下来，`notifystart` 失败本来就只记警告、不影响启动，可以先不管。

## 5. `test_window_length_and_quota`：窗口时长和条数的实测

**决定什么：** 默认的「24 小时 10 条」是用户报告，不是官方的。窗口长度（`quota.window_hours`）、总条数（`quota.window_limit`）要用实测值。

**占额度：** 要一直发到被拒绝为止，会用满一个窗口的额度。**先和使用者说清楚。** 2026-10-17 的那次 E4 只跑其他项，这一项没做（测试骨架里是跳过），要做另问使用者。

**怎么测：** 不影响日常使用的时段：使用者在微信里发一句话（记下这个时刻），之后每隔一段时间发一条（用服务的发送记录），记下**第一次被腾讯拒绝的时刻和已发条数**。窗口时长要等 24 小时以上才能量出来，可以分几天做，每次记下起点。服务把腾讯拒绝后的暂停分钟数、拒绝代码记在事件里（`hubctl events --kind hold`）。

**怎么记：** 总条数上限（第几条开始被拒）、被拒时的错误代码（`ret` 值）、窗口从使用者发话算起多久到期（发话时刻到第一次「不让发」的时刻）。

**回填：** `quota.window_limit`、`quota.window_hours` 的默认值；拒绝代码写进 `hub-quota` 规格里的说明。

## 6. `test_context_token_lifetime`：回复用的对话凭证能用多久

**决定什么：** 有用户说回复用的 `context_token` 只能用 1 到 2 分钟。`reply.handle_minutes`（服务这边的上限，默认 30 分钟）要不要改小，回复被拒绝时项目拿到的原因文字对不对。

**占额度：** 约 6 条（回复，计入回复保留）。

**怎么测：** 取一条使用者消息的 `context_token`，之后每隔一段时间（1、2、5、10、30 分钟……）用它回复一条，记录**第一次被拒绝**的时间。探针按 0、1、2、5、10、30 分钟各回一条（共 6 条、约 35 分钟），第一次被拒绝就停。

**怎么记：** 凭证实际能用多久；被拒绝时腾讯的错误代码；使用者隔了多久再发话时 `context_token` 会变（是不是每条消息一个新的）。

**回填：** `reply.handle_minutes` 的默认值；`hub-inbox` 规格里回复被拒绝时的原因文字。

## 7. `test_one_login_per_wechat`：「一号一绑」是否成立

**决定什么：** 设计按「一个微信号只有一个 ClawBot 绑定，最后一次扫码生效」来做，所以只有服务登录。这一点不确定：10 月 10 日 00:16 到 00:32（东京时间）前后，ashare-quant 的绑定失效过，那段时间使用者可能给别的项目扫过码。

**占额度：** 0 条。**只观察，不要再扫一次码来试**（会挤掉正在用的绑定）。

**怎么测：** 问使用者那段时间有没有给别的项目扫过码；以后有第二个项目接入时，观察掉线的时间点，看是不是在对方扫码之后。

**怎么记：** 把观察到的情况写进本文末尾的结果记录和《设计方案》第 2 节。

**回填：** 成立 → 设计不变，文档里写明「不要为别的项目另外扫码」；不成立（能多号并存）→ 以后可以考虑每个项目一个绑定，但那是另一个变更。

## 8. `test_old_buf_redelivers`：带旧的 `get_updates_buf` 再收，是不是重发同一批消息

**决定什么：** ashare-quant 现在依赖这一点（收消息进度没写回去，下次还能再收到）；服务的「先入队、提交，最后才写回 `get_updates_buf`」的顺序也依赖它：崩溃时同一批消息会被腾讯再给一遍，靠去重键挡住。不重发的话，崩溃时会丢消息。《回退手册》里「退回直连会不会重复收到」也看这一项。

**占额度：** 0 条。

**怎么测：** 收一批消息并记下返回的新 `get_updates_buf`（别当成真处理），再用上一次的（旧的）`get_updates_buf` 请求一次，看是不是重发同一批。探针后面两次要进度只各等 15 秒（有数据腾讯会马上回），免得接着用这条消息的对话凭证的几项等到凭证放旧了。

**怎么记：** 重发 / 不重发；重发时消息的 `message_id`、`seq` 是不是和第一次一样（去重键靠它）。

**回填：** 重发 → 设计成立；不重发 → 崩溃窗口里的消息会丢，要在 `hub-inbox` 规格里写明这个风险。

## 9. `test_long_poll_timeout_round_trip`：长轮询读超时算不算一次完成的往返

**决定什么：** `upstream_down` 告警按「最近一次与腾讯完成往返的时间」判断。没有新消息时长轮询挂到读超时才返回，这算不算完成往返，决定「腾讯连不上」会不会被安静的夜里误报。

**占额度：** 0 条。

**怎么测：** 没有新消息时发一次 `getupdates`（`upstream.poll_timeout` 默认 45 秒），记录从发出到收到返回的耗时、返回体（空的 `msgs` 还是别的）、有没有 `longpolling_timeout_ms`。探针量两次，客户端读超时放宽到 `poll_timeout` 再加 45 秒，这样「腾讯自己回了个空结果」和「挂到我们读超时」分得开；这几分钟使用者不要发消息。

**怎么记：** 是腾讯在约定时间内正常回了一个空结果（HTTP 200），还是挂到客户端读超时。

**回填：** 正常回空结果 → 读超时的那一类按设计算完成往返；挂到客户端超时 → 改 `alerts.upstream_down` 的判断。

## 10. `test_launchd_umask_for_log`：launchd 的 `Umask` 对 `launchd.log` 生不生效

**决定什么：** `launchd.log` 是 launchd 在服务启动**之前**建的，它的权限由 launchd 决定，plist 里的 `Umask` 63（即 077）管不管用要看真机。

**占额度：** 0 条。

**怎么测：** 按《安装说明》装好 launchd 服务（演练用单独的数据目录和 label），启动后 `ls -l ~/.clawbot-hub-rehearsal/logs/`（正式环境是 `~/.clawbot-hub/logs/`）看 `launchd.log` 的权限。

**怎么记：** `-rw-------` 就是生效；不是，记下实际权限。

**回填：** 生效 → 不用动；不生效 → 把 plist 模板里的标准输出和标准错误改指向 `/dev/null`（服务自己已经写 `hub.log`，权限由它自己管），并在安装说明里去掉对 `launchd.log` 的提醒。

**已量到：** 2026-10-17（东京时间）在 Mac mini 上演练时量到，用的是假腾讯，没占额度。`launchd.log` 是 `-rw-------`：`Umask` 63 对这个**文件**生效。但 launchd 替它新建的 `logs/` **目录**是 `drwxr--r--`（0744），`Umask` 对目录不生效；服务启动后约 0.15 秒内把目录改成 0700，并在 `hub.log` 记一条警告「logs 的权限比规定的宽，已改回（目录 0700、文件 0600）」。结论：模板不用动（只更新了里面的注释），第一次装时那条警告是正常的，安装说明第 8 步和「出毛病怎么办」都写明了。

## 11. `test_qr_login_from_home_network`：在家里的网络上扫码

**决定什么：** 云服务器上扫码曾被微信拦（提示「运行环境存在风险」），所以服务装在家里的 Mac mini 上。要确认家里的网络能正常取码、扫码、确认。

**占额度：** 0 条；**这一项会真的绑定一个账号**，所以只在使用者决定正式绑定（或迁移后需要重新扫码）时做，不要为了测试而扫。

**怎么测：** 在家里的网络上运行 `uv run hubctl login`，记录取码、`wait`、`scaned`、`confirmed` 各个状态出现的时间和提示文字。E4 里的探针只取码、查一次状态，**不扫**。

**怎么记：** 能不能正常扫；万一被拦，记下提示的原文。

**回填：** 能扫 → 安装说明的第 6 步照旧；不能 → 记下原文，查是不是网络环境（代理、VPN）的问题。
