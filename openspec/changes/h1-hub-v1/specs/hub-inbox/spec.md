# Spec Delta

## Purpose

规定使用者在微信里发给 ClawBot 的话怎么被收进来、交给哪个项目、项目怎么取、怎么回复。使用者只有一个聊天窗口，所以要有一套规矩决定一句话归谁；这套规矩不能改变 ashare-quant 现在的用法（不带前缀的话一个字不用改）。

服务不理解这些话的意思——"持仓""状态""买 600519 100 1500"怎么认、怎么答，都在各项目里。服务只做：收进来、认人、分发、保证至少送到一次、记下对话凭证好让项目回复。

## ADDED Requirements

### Requirement: 收消息

登录正常时，服务 MUST 在一个后台线程里不停地向腾讯长轮询 `getupdates`（带上次的 `get_updates_buf`，每次最多等 `upstream.poll_timeout` 秒，默认 45，腾讯建议了更长的 `longpolling_timeout_ms` 时用建议值加 10 秒）。收到一批消息 MUST 按这个顺序处理，缺一不可：

1. 在一个数据库事务里：按去重键（腾讯给的 `message_id`，没有就用 `seq`，再没有就用"时间、对话凭证、文字"的摘要）排除已经收过的，把使用者的消息存下来，更新窗口（见 `hub-quota`），为每条算好交给谁、建好待取记录；
2. 事务提交以后，才把新的 `get_updates_buf` 写回凭证文件。

这样服务在两步之间被杀，重启后腾讯会再给一遍，去重键保证不会收两次。错误处理沿用 ashare-quant 现在的做法：长轮询没等到消息（读超时）算没有新消息；连不上、HTTP 5xx、`ret` / `errcode` 非 0 都不能当成"没有新消息"，等一等再收，等待时间从 `upstream.backoff_start`（5 秒）起每次翻倍、最多 `upstream.backoff_max`（60 秒）；-14 见 `hub-login`。

文字取法：这条消息里所有文字项（`type` 为 1）的文字依次拼接；没有文字项（图片、语音、文件……）时 `has_text` 为 false、文字为空。没有对话凭证的消息不能回复，也就不收。

#### Scenario: 收到一句话

- **WHEN** 假上游返回使用者的一条消息 `持仓`，对话凭证 `ctx-1`
- **THEN** 数据库里多一条待取记录，开了新窗口、对话凭证是 `ctx-1`，凭证文件里的 `updates_buf` 更新成上游给的新值

#### Scenario: 重复的消息只收一次

- **WHEN** 假上游把同一条消息（同一个 `message_id`）连续返回两次
- **THEN** 只有一条待取记录，窗口只开一次

#### Scenario: 两步之间被杀

- **WHEN** 事务已提交、`updates_buf` 还没写回时服务被杀，重启后假上游又返回同一批消息
- **THEN** 不产生重复的待取记录

#### Scenario: 腾讯报错不是"没有新消息"

- **WHEN** 假上游对 `getupdates` 回 `ret: 500`，再回 HTTP 502，再恢复正常
- **THEN** 等待时间依次是 5 秒、10 秒，恢复后重新计；期间没有项目收到任何东西，`hubctl status` 里最近一次收消息的错误可见

### Requirement: 只认使用者本人

只有 `from_user_id` 等于凭证里的 `user_id` 的消息才会进入后面的流程。其他人发给 ClawBot 的消息 MUST 被丢弃：不看内容、不转给任何项目、不回复、不开窗口、不记正文；只给"忽略了几条"计数，日志里写数量。腾讯标明是机器人自己发的消息（`message_type` 为 2）同样丢弃。

#### Scenario: 陌生人发来的消息

- **WHEN** 假上游返回一条 `from_user_id` 不是使用者的消息
- **THEN** 没有待取记录，没有回复，窗口不变，`hubctl status` 里"忽略的消息"加 1

### Requirement: 一句话交给谁

服务 MUST 按下面的顺序决定每一句话的去向，第一个命中的生效。匹配时去掉首尾空白，全角空格当空格，英文不分大小写、全角半角视为相同（按 Unicode NFKC 比较）；交给项目的文字是去掉前缀和分隔符以后**原样**的内容（首尾空白去掉），没有前缀的话原样交出。

1. **没有文字**（图片、语音等）：交给默认项目（文字为空、`has_text` 为 false）；没有默认项目就由服务回"没有设默认项目，这句话没处理"。
2. **服务自己的指令**：话是"服务"，或者"服务"后面跟着分隔符（空白或 `:` `：` `,` `，` `、`）：由服务回复，不交给任何项目（见下一条）。
3. **带前缀**：话以某个项目的前缀开头，后面紧跟分隔符或者就此结束：交给那个项目，去掉前缀和分隔符。前缀后面直接连着字（"量化状态"）**不算**带前缀，这样默认项目自己的指令里碰巧以前缀开头的字不会被误拦。项目已停用时由服务回"项目「x」已停用，这句话没处理"。
4. **确认话**：整句话（去掉首尾空白以后）正好是一个确认词（`routing.confirm_words`，默认 对、是、确认、好、ok、yes、y），并且有项目在等确认（见"等确认"）：恰有一个就交给它；有几个就由服务回"有几个项目在等你确认（量化、x），请加前缀，例如“量化 对”"；一个都没有就往下走。
5. **其余的话**：交给默认项目；没有默认项目由服务回"没有设默认项目，这句话没处理：请加项目前缀（发“服务 项目”看有哪些）"。

交给项目的每一条待取记录带着它是怎么路由来的（`via`：`prefix`、`confirm`、`default`）。

#### Scenario: 不带前缀归默认项目

- **WHEN** 默认项目是 ashare-quant（前缀"量化"），使用者发"持仓"
- **THEN** ashare-quant 的待取记录里文字是"持仓"、`via` 是 `default`

#### Scenario: 带前缀归对应项目

- **WHEN** 项目 x 的前缀是 `x`，使用者发"x 状态"、"X：状态"、"x，状态"
- **THEN** 三句都交给项目 x，文字都是"状态"

#### Scenario: 默认项目也能带前缀

- **WHEN** 使用者发"量化 状态"
- **THEN** 交给 ashare-quant，文字是"状态"，`via` 是 `prefix`

#### Scenario: 前缀后面直接连着字

- **WHEN** 使用者发"量化因子"（前缀"量化"后面没有分隔符）
- **THEN** 当作没有前缀，原样交给默认项目

#### Scenario: 不认识的前缀

- **WHEN** 使用者发"foo 状态"，没有叫 foo 的前缀
- **THEN** 原样（含"foo"）交给默认项目

#### Scenario: 只发了一个前缀

- **WHEN** 使用者发"x"
- **THEN** 交给项目 x，文字为空，`has_text` 为 true

#### Scenario: 图片

- **WHEN** 使用者发了一张图片（没有文字项）
- **THEN** 交给默认项目，文字为空、`has_text` 为 false；没有默认项目时服务回一句"没有设默认项目，这句话没处理"

#### Scenario: 没有默认项目

- **WHEN** 没有默认项目，使用者发"持仓"
- **THEN** 没有项目收到；服务回"没有设默认项目……"

### Requirement: 服务自己的两个指令

服务只认两个指令，回复第一行带 `【服务】`（标签 `hub.label`，默认"服务"），算"回复"一类的条数：

- `服务 项目`：列出每个启用项目的前缀、是不是默认、在不是在线，例如 `量化（默认，在线）：不加前缀的话都给它，也可以写“量化 …”`。只推送的项目不列。
- `服务 状态`：登录状态、对话窗口还剩多久、已用 / 总条数、各项目在不在线，不含任何凭证和密钥。

"服务"后面是别的字（或没有字）时回一句"我只认两个指令：服务 项目、服务 状态"。

#### Scenario: 服务 项目

- **WHEN** 使用者发"服务 项目"，启用着 ashare-quant（前缀量化、默认、在线）和 x（前缀 x、离线）
- **THEN** 收到的回复第一行是 `【服务】`，里面有"量化（默认，在线）"和"x（离线）"；没有交给任何项目

#### Scenario: 服务 状态不带凭证

- **WHEN** 使用者发"服务 状态"
- **THEN** 回复里有登录状态、窗口剩余、已用条数；找不到 `bot_token`、`context_token`、项目密钥

#### Scenario: 服务的回复算回复

- **WHEN** 使用者发"服务 状态"，服务回复一条
- **THEN** 新窗口里"回复"一类的已用条数是 1（记在服务自己名下），不占任何项目的保底和上限；这句话本身开了新窗口，所以一定有额度可回

#### Scenario: 服务也不理解别的话

- **WHEN** 使用者发"服务 重启"
- **THEN** 服务回"我只认两个指令：服务 项目、服务 状态"，什么也没改

### Requirement: 等确认

项目在回复里带 `awaiting_confirmation: true` 并且发送成功（见 `hub-send`），就是在告诉服务"我在等使用者回确认话"：服务 MUST 记下这个项目等到什么时候（`confirm_seconds`，默认 600 秒）。这个标记在下面任何一种情况出现时清掉：到期；使用者的下一句话交给了这个项目（不管是什么话——和 ashare-quant "回'对'之外的任何一句都让等确认的那一笔作废"一致）；它被一句确认话消耗了；项目被停用；项目不在线。

标记只影响第 4 步的确认话，不影响带前缀的话。

#### Scenario: 对不串线

- **WHEN** 项目 A 的回复带 `awaiting_confirmation: true`（等确认），项目 B 没有，使用者发"对"
- **THEN** "对"交给 A，`via` 是 `confirm`

#### Scenario: 几个项目同时在等

- **WHEN** A、B 的回复都带 `awaiting_confirmation: true`，使用者发"对"
- **THEN** 没有项目收到；服务回"有几个项目在等你确认（量化、x），请加前缀，例如“量化 对”"；使用者再发"量化 对"，交给 A

#### Scenario: 超过 10 分钟

- **WHEN** A 等确认，11 分钟后使用者发"对"
- **THEN** 当作没有项目在等，原样交给默认项目

#### Scenario: 中间说了别的

- **WHEN** A 等确认，使用者先发"持仓"（交给默认项目 A），再发"对"
- **THEN** "持仓"交给 A 的同时清掉了等确认的标记；"对"当作没有项目在等，交给默认项目（A 回"没有等你确认的记录"，和现在一致）

#### Scenario: 没有人在等

- **WHEN** 没有项目在等确认，使用者发"对"
- **THEN** 原样交给默认项目

### Requirement: 项目没在线

交给一个**不在线**的项目（定义见 `hub-projects`）的话，服务 MUST 仍然把它放进这个项目的待取队列，保留 `inbox.retention_minutes`（默认 10）分钟，并马上回使用者一句：`「<项目名>」现在没在线。这句话我先留着：<N> 分钟内它回来就会处理，超过就作废`。同一个项目的这句提醒 `inbox.offline_notice_seconds`（默认 300）秒内最多发一次，免得使用者连发几句就把额度用光。项目停用时的提醒同样限频。保留期从**收到**起算（服务停了很久以后补收到的旧消息也会交出去，项目用消息自带的时间自己判断要不要注明"回复你 HH:MM 发的消息"）。

#### Scenario: 项目没在线

- **WHEN** 项目 x 90 秒内没有取过话，使用者发"x 状态"
- **THEN** 使用者马上收到服务的回复，说明 x 没在线、话留 10 分钟；这句话在 x 的队列里

#### Scenario: 回来以后接着处理

- **WHEN** 上面的 x 在 5 分钟后开始取话
- **THEN** 取到"状态"，`attempt` 为 1

#### Scenario: 超时作废

- **WHEN** x 在 11 分钟后才回来取话
- **THEN** 取到的是空，那条记录标成"过期"

#### Scenario: 连发几句只提醒一次

- **WHEN** 项目 x 没在线，使用者 1 分钟内给它发 3 句话
- **THEN** 使用者只收到一条"没在线"的提醒

### Requirement: 取话

`GET /v1/inbox?wait=<秒>&max=<条数>` MUST 返回分给调用方这个项目的话，不含别的项目的：

```json
{
  "items": [
    {"id": "m_9f3a1c20", "text": "持仓", "has_text": true,
     "at": "2026-10-12T08:31:02+08:00", "at_ms": 1791763862000,
     "received_at": "2026-10-12T08:31:03+08:00", "attempt": 1,
     "via": "default", "reply_handle": "rh_Zk3pQ2..."}
  ],
  "lease_seconds": 60
}
```

- `wait`：没有话时最多等几秒再返回空列表，默认 `inbox.wait_seconds`（25），最大 `inbox.max_wait`（55），0 表示不等；等的时候一有新话立刻返回。
- `max`：最多返回几条，默认 10，最大 50。
- 返回的话按收到的先后排；每一条被**租出去** `inbox.lease_seconds`（默认 60）秒，租期内不会再给；租期过了还没确认，下次取话时再给一次，`attempt` 加 1。最多给 `inbox.max_attempts`（默认 5）次，之后作废并记一条事件。
- 同一个项目同一时间只留一个正在等的取话请求：新的来了，旧的马上返回空列表。
- 每个项目的队列最多 `inbox.max_queued`（默认 50）条，超了丢最旧的没租出去的，并记一条事件。
- 只推送的项目（`--push-only`）调这个接口：403 `push_only`。

#### Scenario: 有话立刻返回

- **WHEN** 队列里有一条话，项目调 `GET /v1/inbox?wait=30`
- **THEN** 马上返回这一条，不等

#### Scenario: 没话就等

- **WHEN** 队列是空的，项目调 `GET /v1/inbox?wait=2`，1 秒后使用者发来一句话
- **THEN** 大约 1 秒时返回这句话；如果没人发话，大约 2 秒时返回空列表

#### Scenario: 没确认会再给

- **WHEN** 项目取走一条话但没确认，租期 60 秒过去后再取
- **THEN** 再次拿到同一条（同一个 `id`），`attempt` 是 2；在租期内再取不会拿到

#### Scenario: 超过最多次数

- **WHEN** 同一条话被租出 5 次都没确认
- **THEN** 第 6 次取话拿不到它，事件里有一条"作废"的记录

#### Scenario: 只看得到自己的

- **WHEN** 使用者先后发了给项目 A 和项目 B 的话，两个项目各自取话
- **THEN** 各自只拿到自己的

#### Scenario: 新请求顶掉旧请求

- **WHEN** 项目有一个取话请求正在等，同一项目又发来一个
- **THEN** 旧的马上返回空列表，新的继续等

### Requirement: 确认

`POST /v1/inbox/ack`，请求 `{"ids": ["m_…", …]}`（最多 50 个），MUST 把这些话标成"已处理"：不再给，并**立即清掉它们的正文**（回复用的对话凭证留到句柄过期）。返回 `{"acked": <n>}`；`ids` 里不认识的、不属于调用方的、已经确认过的都不报错（幂等），算在 `unknown` 里一起返回，不透露是哪一种。

项目 SHOULD 在**处理完**以后再确认（先确认后处理会在项目挂掉时丢话；先处理后确认会在挂掉时多处理一次，项目对同一句话处理两次应当无害）。

#### Scenario: 确认以后不再给

- **WHEN** 项目取到一条话，确认，租期过后再取
- **THEN** 取不到它；数据库里这条记录没有正文

#### Scenario: 重复确认

- **WHEN** 同一个 `id` 确认两次，或者确认一个别的项目的 `id`
- **THEN** 都是 200，第二次 / 别人的出现在 `unknown` 里，没有任何副作用

### Requirement: 回复句柄

每条取到的话带一个不透明的回复句柄 `reply_handle`（`rh_` 加 22 个 URL 安全的随机字符）。项目用它调 `POST /v1/replies`（见 `hub-send`）。句柄 MUST：

- 只对被路由给这个项目的那条话有效；别的项目拿到它、或者根本不存在，都是 404 `unknown_handle`（两种情况返回一样）；
- 在话被收到之后 `reply.handle_minutes`（默认 30）分钟内有效，过了是 410 `handle_expired`，同时清掉那条话的对话凭证；
- 不含任何对话凭证的信息（句柄和 `context_token` 之间只有数据库里的对应关系，对话凭证从不出现在任何接口里）。

#### Scenario: 句柄用别人的

- **WHEN** 项目 B 用项目 A 的句柄回复
- **THEN** 404 `unknown_handle`，没有发任何东西

#### Scenario: 句柄过期

- **WHEN** 话收到 31 分钟后，项目才回复
- **THEN** 410 `handle_expired`，没有发任何东西

#### Scenario: 句柄里没有凭证

- **WHEN** 检查所有 `reply_handle`
- **THEN** 它们都是随机字符，不是对话凭证的编码或截取

### Requirement: 清理

服务 MUST 定期（每分钟）清理：过了保留期还没取走的话标成"过期"并清掉正文；已确认或过期的待取记录保留 7 天（只有编号、项目、时间、路由方式、字数、结果，没有正文和对话凭证），之后删除；去重键保留 7 天。窗口、发送记录和事件的保留期见 `hub-deploy`。

#### Scenario: 过期的话没有正文

- **WHEN** 一条话在队列里放了 11 分钟没人取
- **THEN** 它的状态是"过期"，数据库里正文为空
